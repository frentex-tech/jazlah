# Decisions and open questions (JAZLA API)

Two lists. **Open questions** are things nobody has decided: do not guess them, ask. The **decisions in force** are what has been decided, so the next session does not decide it again differently.

Paths are relative to `services/api/`.

## How to use this file

- Your task depends on an open question: stop and ask the user. If they tell you to proceed anyway, put the assumption behind an interface or a config value, mark it in the code with a comment that starts `ASSUMPTION:`, and list it in your report.
- The user answers an open question: delete the row and add a line to the decisions.
- You make an architectural decision while working (a new shared building block, a new convention, a new dependency the user approved, a pattern the next module should copy): add a dated line under the right heading in the same change, update the rule file it affects, and update `.claude/ARCHITECTURE.md` if it changes the layout. A decision that lives only in a chat transcript will be made again, differently.
- A decision listed here is changed only by the backend owner. If you think one is wrong, say so in your report.

### Project and platform

- **Standalone project.** `services/api/` has its own `package.json` and lockfile. No workspace and no Turborepo. Decided 2026-11-13. Why: the build proceeds one small step at a time, and the API must stand on its own.
- **Source of truth.** Stated once, at the top of `CLAUDE.md`. Decided 2026-11-13.
- **Stack.** NestJS 12, TypeScript 6 `strict`, Jest, ESLint 10 with typescript-eslint, pnpm. Decided 2026-11-13, replacing NestJS 11, TypeScript 5 and ESLint 9. Why: Nest 11 would have pinned Swagger to an old major from its first day, and ESLint 9 reached end of life on 2026-08-06. TypeScript stays on 6 because ts-jest, typescript-eslint and the Nest tooling do not accept TypeScript 7.
- **CommonJS.** The project compiles to CommonJS (`module: nodenext` with no `"type": "module"`); Nest 12's ESM-only packages are loaded through Node's `require(esm)`. Decided 2026-11-13. Why: the Nest 12 CommonJS template keeps Jest and the existing path aliases unchanged, while the ESM template moves to Vitest. Moving to ESM later is its own step.
- **Node 26.** `engines.node >=26`, `@types/node ^26`, `.nvmrc` 26. Decided 2026-11-13, replacing Node 24. Why: Node 26 was the current LTS when the project started (LTS from 2026-10-28, supported until 2029-04-30).
- **Linting is ESLint, not oxlint.** The Nest 12 template generates oxlint; this project keeps ESLint 10 because the planned folder boundary rules are written as ESLint rules. Decided 2026-11-13.
- **Database.** PostgreSQL 17 with PostGIS, through Prisma with a multi-file schema, one schema file per domain. Local image `postgis/postgis:17-3.5`. Why *(inferred)*: PostGIS is needed for coverage polygons, and each domain owns the file that holds its models.
- **Prisma 7.10.1, pinned exactly.** `prisma`, `@prisma/client` and `@prisma/adapter-pg` at 7.10.1: npm's `latest` tag points to an 8.0 release candidate. The `prisma-client` generator emits CommonJS (`moduleFormat = "cjs"`, bare imports) into `src/infra/database/generated/prisma/` (gitignored, not linted, skipped by the registry check); PostgreSQL is reached through the pg driver adapter with a 5 s connection timeout; `prisma.config.ts` holds the URL and loads `.env` with dotenv. Decided 2026-11-13.
- **Local database.** `docker-compose.yml` runs `postgis/postgis:17-3.5` with databases `jazla` and `jazla_test`, on host port `JAZLA_DB_PORT`, default 5434, because 5432 and 5433 were taken on the first machine. e2e tests use `jazla_test`, derived from `DATABASE_URL` by `scripts/e2e.mjs` (database name + `_test`), which applies migrations first. Decided 2026-11-13 by the session.
- **PostGIS is enabled by the first migration** (`CREATE EXTENSION IF NOT EXISTS postgis`, added by hand). Prisma 7 leaves the extension's objects alone: `prisma migrate diff` against a PostGIS database reports no change. Decided 2026-11-13.
- **Readiness.** `GET /v1/health` is liveness and touches nothing; `GET /v1/health/ready` checks each dependency in parallel (the database with `SELECT 1` and Redis with `PING`, 1 s timeout each) and answers `{ status, checks }` with 200 or 503, not the error shape, so 200 and 503 have one shape. The failure is logged, never returned. Decided 2026-11-13 by the session.
  - **Redis on the right database (foundation review, batch B).** The Redis check sends `CLIENT INFO` instead of `PING` and reports Redis down when the connection is not on the database `REDIS_URL` names. Why: when Redis refuses the database (SELECT fails: fewer databases on the server, or cluster mode), ioredis emits an error, then becomes ready on database 0 and answers PING (checked against ioredis 6.0.0 and the local Redis 7), so the API would use another environment's data while readiness said up. `REDIS_URL` itself now accepts only databases 0 to 15 and only the lowercase `redis://` and `rediss://` schemes (`REDISS://` passed the check, which lowercases, but ioredis then connected without TLS). Decided 2026-11-13 by the backend owner (foundation review, batch B); CLIENT INFO as the means by the session.
- **Prisma conflict details.** With the pg adapter, Prisma 7 reports a unique violation by constraint name, not its fields. CONFLICT `details` is `{ constraint, fields? }`: fields for a primary key (`['id']`, by convention) and when the driver reports them. Resolving other constraint names to fields would need a catalog lookup; not built. Decided 2026-11-13 by the session.
- **Unique constraints become specific error codes in the repository.** A repository matches the constraint names it knows (named explicitly in the schema, `<table>_<columns>_key`) and throws a specific code (for example PHONE_ALREADY_REGISTERED); `mapPrismaError`'s generic CONFLICT is the fallback for the rest. No catalog lookup. Decided 2026-11-13 by the backend owner (step five brief). Rules 12a and 17a in `.claude/rules/database.md`.
- **Redis 7 with BullMQ.** Versions pinned exactly: `bullmq` 6.7.6 (npm `latest`), `@nestjs/bullmq` 12.0.2, `ioredis` 6.0.0 (the version BullMQ 6.7.6 is built and tested against; an optional peer of BullMQ 6). Decided 2026-11-13 by the session.
- **Local Redis.** `docker-compose.yml` runs `redis:7-alpine` with an append-only file (fsync every second), `maxmemory-policy noeviction` (BullMQ requires it) and a named volume, on host port `JAZLA_REDIS_PORT`, default 6380, because 6379 was taken on the first machine. `pnpm infra:up` / `infra:down` manage both services; `db:up` / `db:down` were removed (nothing depended on them). e2e runs use the next logical Redis database (`/0` → `/1`), derived by `scripts/e2e.mjs`, and remove their queues afterwards. Decided 2026-11-13 by the session.
- **One shared Redis client, BullMQ's own connections.** `RedisService` (ioredis) is for general use; BullMQ opens its own connections from `{ url: REDIS_URL }` for every queue and worker, as its documentation recommends (workers need `maxRetriesPerRequest: null`). Decided 2026-11-13 by the backend owner (step five brief).
  - **Correction (foundation review, batch B): neither fails fast.** This entry said the shared client "fails a command fast while Redis is down" and that "producers fail fast". Both were wrong. The shared client (`maxRetriesPerRequest: 1`, offline queue on) holds a command while it reconnects; the review measured each rate limit call waiting the full 500 ms timeout. Producer connections keep ioredis's defaults (20 retries with BullMQ's backoff), so `queue.add` against an unreachable Redis was still pending after 60 s. Code that must not wait checks `status === 'ready'` or bounds the call with `withTimeout`; the rate limit storage does both.
  - **Producers now fail fast (foundation review, batch C).** Every registered queue is a `BoundedQueue` (`src/infra/queue/bounded-queue.ts`, set as @nestjs/bullmq's queue class by `QueueRegistrationModule`, so R15 covers every queue): `add` and `addBulk` check the queue's own connection and refuse at once with SERVICE_UNAVAILABLE (503) while it is not `ready`, and bound the add to `QUEUE_ADD_TIMEOUT_MS` (500 ms) while connecting or when Redis is slow. Measured with Redis stopped behind a TCP proxy (`test/queue.e2e-spec.ts`): five adds answered 503 in 500.9 ms, 0.1 ms, 0.0 ms, 0.0 ms and 0.0 ms. The first waits the 500 ms because the client still reports `ready` until it notices the dropped socket; that add was sent, so it may still land when Redis returns, which is why a retried add uses `buildJobId`. Before the change, the same add was still pending after 3 s (measured) and the earlier review measured over 60 s. Why the status check rather than `enableOfflineQueue: false` on the queue connection: @nestjs/bullmq gives each worker its queue's connection options, and the workers must keep waiting for Redis. Decided 2026-11-14 by the backend owner (foundation review, batch C); the mechanism by the session.
  - **Observed, not fixed: BullMQ 6.7.6 workers can hang in `close()` after their connection dropped and came back**, with the client `ready` again (seen twice in the producer test while the app's workers shared the proxied connection; the producer test now runs without processors). If it happens in production, shutdown waits for the orchestrator's SIGKILL. Not investigated further in batch C.
- **Queue folder is `src/infra/queue/`**, replacing the `src/infra/jobs/` named earlier. Decided 2026-11-13 by the backend owner (step five brief).
- **Queue registration with an error listener.** Every queue is registered with `QueueRegistrationModule.register`, which sends queue `error` events to the logger at warn; lint rule R15 refuses `BullModule.registerQueue` outside `src/infra/queue/`. Decided 2026-11-13 by the backend owner (step six brief).
- **Deterministic job ids stop duplicate enqueues, not duplicate work.** `buildJobId` makes BullMQ ignore an add while a job with that id is waiting, delayed, active, or kept after it ended (completed: 1 day, at most 1,000; failed: 14 days). A failed job blocks re-adding until it is removed; once removed, the id enqueues again; retries, stalled jobs and shutdown cancellations run the same job again. Work that must happen exactly once records an idempotency key in the database inside the transaction that does the work: `IdempotencyRunner.runOnce(operation, key, work)` over the table `idempotency_keys` (unique `idempotency_keys_operation_key_key`). It claims the key with `INSERT ... ON CONFLICT DO NOTHING` (Prisma `createMany` with `skipDuplicates`) before the work, so a concurrent run waits on the unique index and then returns the stored result; the result is stored as JSON and returned to every repeat; work that throws deletes the claim. Decided 2026-11-14 by the backend owner (foundation review, batch C, finding 17); the claim-first design, the `{ value }` outcome and the table's columns by the session.
- **Job logging on the worker's events.** `JobProcessor` intercepts @nestjs/bullmq's assignment of `_worker` and attaches `JobLifecycleLogger` to the worker's `active`, `completed`, `failed` and `stalled` events, plus the error listener and the shutdown timer. Why: logging inside `process` (as before) missed the final failure of a stalled job (BullMQ fails it in the worker without calling the processor), logged BullMQ's control-flow errors (DelayedError, WaitingChildrenError, RateLimitError) as failures, logged "completed" before BullMQ stored the completion, and a subclass overriding `onApplicationBootstrap` dropped the listeners. Lint rule R17 keeps WorkerHost, QueueEvents and FlowProducer (and their @nestjs/bullmq helpers) inside `src/infra/queue/`; R18 forbids a processor from defining `process` or `_worker`. Processors must be safe to run beside a retry of themselves. Decided 2026-11-14 by the backend owner (foundation review, batch C, findings 18 to 20); intercepting `_worker` and forbidding QueueEvents and FlowProducer (rather than wrapping them) by the session.
- **Event bus.** `@nestjs/event-emitter` 12.0.3, pinned exactly, wrapped in `src/infra/event-bus/` (only importer: lint rule R16). Events are `DomainEvent<'domain.entity.action'>` classes with a static `eventName`; subscribers name the class (`@OnDomainEvent`), so the compiler rejects a non-event and a wrong payload. Subscribers run asynchronously (`setImmediate`), and their errors are logged with the event and subscriber names. Decided 2026-11-13 by the backend owner (step six brief); the typing approach by the session.
  - **Correction and change (foundation review, batch C, findings 22 and 23).** `DomainEvent` and its types moved to `src/common/events/`, plain TypeScript, so a module's `domain/` can extend it under R8 (it was in `src/infra/`, which `domain/` may not import). The comments claimed the bus refused a class whose static name differed from its type; only `@OnDomainEvent` checked that, and `publish(event)` checked nothing about the class (a type cannot reach an instance's constructor). `publish` now takes the class too, `publish(OrderPlacedEvent, event)`, typed with `DomainEventClass`, so a non-event, a class without a static name, a mismatched name and an event under another class's name do not compile (`test/types/event-bus.type-test.ts`); a run-time check still guards casts. Decided 2026-11-14 by the backend owner (batch C); passing the class by the session.
- **Ambient transactions.** The open transaction lives in the AsyncLocalStorage scope. Repositories and CRUD services query through `DbContext.client` (the scope's transaction client, or the root client outside one); use cases open transactions with `TransactionRunner.run`. `runInTransaction` called inside a scope joins it whatever client it is given; an independent transaction from inside one is not supported. `DbClient` parameters were removed. Decided 2026-11-13 by the backend owner (foundation review, batch A), replacing the client passed down by hand, which let a root client inside a transaction open a second, independent one.
- **A database error ends the transaction.** A Prisma query extension (`trackQueryFailures`) marks the scope failed when any query in it fails; if the work then returns normally, `runInTransaction` rolls back and rejects with TransactionAbortedError (INTERNAL_ERROR), dropping after-commit callbacks. Strict on purpose: even an expected failure, such as `findUniqueOrThrow` finding nothing, ends the transaction; use `findUnique`, `upsert` or `ON CONFLICT`. Decided 2026-11-13 by the backend owner (foundation review, batch A); the extension as the mechanism by the session.
- **No external I/O inside a transaction**, and write conflicts are retried: P2034 reruns the transaction up to 3 times with full-jitter delays (25 ms base, doubling), then TRANSACTION_CONFLICT (409). Decided 2026-11-13 by the backend owner (foundation review, batch A); the attempt count and delays by the session.
- **Database pool and transaction defaults are config**: DATABASE_POOL_SIZE 10, DATABASE_CONNECTION_TIMEOUT_MS 5000, DATABASE_TRANSACTION_TIMEOUT_MS 5000, DATABASE_TRANSACTION_MAX_WAIT_MS 2000, DATABASE_ISOLATION_LEVEL ReadCommitted (Prisma's and pg's previous implicit defaults, now stated). Decided 2026-11-13 (foundation review, batch A).
- **Database errors mapped.** P2007, P2000 and P2020 to BAD_REQUEST; P2010 by its driver error kind; P2028 and an unreachable or overloaded database (P1001, P1008, P1017, P2037, pg's connection timeout) to the new SERVICE_UNAVAILABLE (503); P2034 to the new TRANSACTION_CONFLICT (409); check and exclusion violations to CONFLICT. Prisma reports those as P2039, its code for any unclassified PostgreSQL error, so only SQLSTATE 23514 and 23P01 are mapped and every other P2039 stays INTERNAL_ERROR. Decided 2026-11-13 by the backend owner (foundation review, batch A); P2020 and the P2039 narrowing by the session.
- **Events wait for the commit.** `runInTransaction` keeps an after-commit list in AsyncLocalStorage; `EventPublisher` adds to it through `runAfterCommit`. Delivered after the outermost commit, dropped on rollback, dispatched at once outside a transaction. Decided 2026-11-13.
  - **The scope has a state (foundation review, batch C, finding 21).** `TransactionScope.state` is `open`, then `committed` or `rolled-back`. Async work started inside a transaction keeps its scope after it ends; before, a callback it registered was pushed onto a list that had already run and was silently lost. Now it runs at once after a commit, and is dropped with a warn after a rollback. Every callback runs isolated (`runIsolatedCallback`), outside a transaction too: a throw or a rejected promise is logged at error and stops neither the caller nor the other callbacks (a throw outside a transaction used to reach the caller, and a rejected promise was unhandled). Decided 2026-11-14 by the backend owner (batch C).
- **runInTransaction joins by scope.** Corrects step four: Prisma 7 transaction clients have `$transaction`, so the shape test (`'$transaction' in client`) never joined and a nested call opened a nested transaction. It now joins when given the transaction client of the scope it runs in. Decided 2026-11-13 by the session.
- **Events only for losable effects.** Notifications, realtime updates, cache invalidation. An effect that must happen goes through a job with a deterministic id. Ledger entries are written in the same transaction through the finance module's service. **Planned:** a transactional outbox for payment webhooks, built with the payments module. Decided 2026-11-13 by the backend owner (step six brief).
- **Bounded worker shutdown.** `@nestjs/bullmq` closes workers in `onModuleDestroy` and waits without limit. `JobProcessor` starts a 25 s timer when its worker starts closing; when it ends, the active jobs' abort signals fire and the jobs end with `JobCancelledError`, so BullMQ retries them later. The database and Redis clients close in `onApplicationShutdown`, after the workers, so a finishing job can still use them (PrismaService moved there from `onModuleDestroy`). Decided 2026-11-13 by the session.
- **Workers by role.** Production runs API processes and worker processes separately, from the same build: `QUEUE_WORKERS_ENABLED` is false for an API process and true for a worker process. Why: job load at peak times (Eid al-Adha) must not slow down API responses; a worker process is scaled on its own, and an API process spends no CPU or connections on jobs. The variable is required in production (no default, startup fails without it, as for TRUST_PROXY_HOPS) and true elsewhere when unset, so a developer's single process runs everything. Processors and schedulers are provided through `provideWorkers` (`src/infra/queue/`), which, when off, provides an inert object instead: @nestjs/bullmq finds processors by the class of each provider's instance and Nest runs lifecycle hooks on that instance, so no worker connection opens and nothing is scheduled; queues and producers work as usual. e2e apps start with workers off (`scripts/e2e.mjs`) and a suite turns on only the worker it needs (`workers: [...]`, an `overrideProvider(X).useClass(X)`), which removed the list of module processors `createQueueProbeApp` had to keep. Decided 2026-11-14 by the backend owner (issue #229 corrections); the variable name and the factory mechanism by the session.
- **Object storage.** Described as "S3-compatible", reached through the storage port, no vendor named. Why *(inferred)*: hosting is not chosen yet, and the port makes the vendor a configuration value.
- **Payment gateway.** Geidea, behind the payments port. Why: the backend owner's decision; no reason recorded.
- **Scope.** A multi-vendor platform: JAZLA's own products plus partner merchants, contracted kitchens, per-merchant commission, weekly transfers, and cash on delivery collected by the delivery company. Summary in `.claude/ARCHITECTURE.md`.
- **Brand spelling.** JAZLA in these files.

### Workflow

- **Git.** Make no commits and create no branches unless the user asks in that session. Decided 2026-11-13. The guards for `.env` files and committed migrations in `.claude/settings.json` stay.
- **Lint rules enforce the architecture.** `eslint-plugin-boundaries` (`boundaries/dependencies`, with `checkAllOrigins`, `checkInternals` and `checkUnknownLocals` on and `default: "disallow"`) and `eslint-import-resolver-typescript` enforce R1 to R8; typescript-eslint, `no-restricted-properties`, `no-console` and `@eslint-community/eslint-plugin-eslint-comments` enforce R9 to R13. Every message starts with its rule id. Fixtures in `lint-fixtures/` prove each rule, checked by `pnpm lint:rules`, which is part of "done". Decided 2026-11-13, replacing the scaffold's default ESLint config.
- **Packages allowed in `domain/`: none.** `DOMAIN_ALLOWED_PACKAGES` in `eslint.config.mjs` is empty, and Node core modules are refused too. A package may be added only if it is pure utility (no I/O, no framework, no global state), with the backend owner's approval recorded here and a conforming fixture. Decided 2026-11-13 by the session. Why: a domain that imports nothing can be tested and reused without any runtime.
- **Tests keep the full rule set.** No rule is relaxed for tests in the config, with one exception: R21 does not apply to unit tests (`*.spec.ts`), whose partial test doubles (`{ … } as unknown as RedisService`) are typed fakes written in the test, not values from outside the program; `test/` is outside R21's scope (`src/` only) for the same reason. Decided 2026-11-13 by the session; the R21 exception 2026-11-14 (batch D). *Superseded:* tests may no longer disable an R9 rule (R12, below).
- **Lint gaps closed (foundation review, batch D).** Each rule below has violating and conforming fixtures, the bypass the review found among them. Decided 2026-11-14 by the backend owner; the mechanisms by the session.
  - **R0 has its own checker entry and refuses loose files.** Its fixture (an import of a local file outside every element) fails `pnpm lint:rules` when the boundary default is switched to allow or `checkUnknownLocals` is turned off (both verified). A file directly in `src/modules/` or `src/integrations/`, or in an unknown top-level folder of `src/`, is refused by path (`LOOSE_FILES`, a `Program` selector), not by `boundaries/no-unknown-files`, because the element patterns that would make such files unknown need the plugin's deprecated `mode` option.

To make `errors/` plain, `AppError.status` and `ERROR_STATUSES` are plain numbers instead of Nest's `HttpStatus`, and `FieldErrorDto` (Swagger) moved to `src/common/filters/`.
  - **R11 extended** to `import { env } from 'process'`/`'node:process'`, namespace and default imports of `process` (`no-restricted-imports`), destructuring, and `globalThis.process.env` (a selector). `require('process')` and `import x = require('process')` are not covered (no CommonJS `require` in our TypeScript): review rule.
  - **R12 hardened.** Only `eslint-disable-next-line` and `eslint-disable-line` are allowed (`no-use`), each naming its rules (`no-unlimited-disable`), with a reason, and never naming a boundary rule, an R9 or R10 rule, or the rules carrying R11 and R14 to R21 (`no-restricted-disable`). ### Shutdown

- **An overall shutdown deadline (foundation review, batch D).** `main.ts` closes the app on SIGTERM or SIGINT through `shutdownOnSignals` (`src/infra/shutdown/`) instead of Nest's `enableShutdownHooks`, which waits without limit. Past `SHUTDOWN_DEADLINE_MS` (default 28,000, range 1,000 to 29,000: under a typical 30 s grace period, above the 25 s jobs get) the process logs at error `stillClosing` (the resources that began closing and never finished: workers, queues, the database and Redis report themselves through `trackClosing`/`closingResources`) and exits with code 1. Why: BullMQ 6.7.6 workers were seen never to finish closing after a Redis reconnect, which would hold every deploy until the orchestrator's SIGKILL, with nothing logged. The timer keeps the process alive while the close runs (otherwise a close stuck on a promise with nothing else open exits with 0) and is unreferenced after a clean close. A clean close now exits with code 0 instead of re-raising the signal. Proven by `test/shutdown.e2e-spec.ts` (a child process with a resource that never closes: exit code 1, the log line naming it). Decided 2026-11-14 by the backend owner (batch D); the mechanism and the default by the session.

### Structure

- **Top-level folders.** `src/config`, `src/common`, `src/infra`, `src/integrations`, `src/modules`.
- **Infrastructure folder.** `src/infra/` holds health, the HTTP setup, API docs, rate limiting, database, queue, realtime, the event bus, redis and logger. Why *(inferred)*: one place for the infrastructure we run ourselves, apart from business code.
- **Health is infrastructure.** `src/infra/health/`, served at `GET /v1/health`. Decided 2026-11-13. Why: it will check the database and Redis in later steps.
- **Jobs.** `src/infra/queue/` holds the BullMQ connection, the default job options, the queue name list and the shared helpers only; each module registers its own queue. A processor that runs business logic lives inside the module that owns that logic. Why: `infra` must not import from `modules`. Payloads carry ids and processors are idempotent (`.claude/rules/modules.md`, "Jobs").
- **Realtime.** `src/infra/realtime/` holds the socket gateway, room conventions and a publishing port. Modules publish through the port and never import the gateway. Why: same.
- **Event bus.** Modules communicate through an in-process event bus. Publishers and subscribers both live in modules; the bus lives in `infra`. Why: this is how notifications, realtime updates and jobs react to orders without any import from `infra` into `modules`.
- **Four-layer modules.** orders, checkout, payments, refunds, wallet, finance use `api/`, `application/` (one class per use case), `domain/`, `infrastructure/`. Every other module starts as controllers + service + dto and is promoted when it gains a state machine or money logic. Why *(inferred)*: layers where the rules justify them, and no empty layers elsewhere.
- **No inventory module for now.** Product availability belongs to `catalog` and slot capacity to `scheduling`.
- **Order status.** Changes happen in one place only: the state machine in the orders domain layer. No other code sets an order's status.
- **Path aliases.** `@config/*`, `@common/*`, `@infra/*`, `@integrations/*`, `@modules/*`, declared in `tsconfig.json` (read by `jest.config.ts` for unit tests) and repeated in `test/jest-e2e.json`. Imports that cross a top-level folder use the alias. Decided 2026-11-13.

Decided 2026-11-13 by the backend owner (step seven brief); the code-based signature by the session.
- **helmet 8.3.0 with its defaults**, pinned exactly, on every response, `/docs` included. Decided 2026-11-13 by the backend owner (step seven brief); credentials and exposed headers by the session.

  - **Required in production (foundation review, batch B).** With `NODE_ENV=production` the variable has no default and startup fails without it (an empty value counts as unset); elsewhere it defaults to 0. Forgotten behind a load balancer, 0 makes every customer share the load balancer's counter.
- **Rate limiting.** `@nestjs/throttler` 6.7.1, pinned exactly, with its guard global. The storage is our own `RedisThrottlerStorage` (`src/infra/rate-limit/`), built on the shared Redis client: one Lua script per request, fixed window, block on overflow, keys SHA-256-hashed under `jazla:rate-limit:`. Why not a package: the community storage the Nest documentation points to, `@nest-lab/throttler-storage-redis` 1.2.0 (last release 2026-02-03), declares peer `@nestjs/common` and `@nestjs/core` `^7 … ^11`, so it does not support Nest 12. Its predecessor `nestjs-throttler-storage-redis` 0.5.1 stopped in 2024 at Nest 10. Decided 2026-11-13 by the session, as the brief allowed.
- **The default limit is per client address across all endpoints.** The library's default key is per address per endpoint; ours (`clientRateLimitKey`) makes it one counter per address. `@RateLimit(...)` gives an endpoint a stricter limit on a counter of its own, so an OTP limit is not used up by browsing. Defaults: 300 requests per 60 s (`RATE_LIMIT_MAX_REQUESTS`, `RATE_LIMIT_WINDOW_MS`). The number is the session's: mobile carriers put many customers behind one address (carrier-grade NAT), so the default leaves headroom. Revisit with real traffic. Health is exempt (`@SkipRateLimit`). A request to an unknown route (404) is not counted by this limit, because guards run only on matched routes; the pre-routing limit counts it. Decided 2026-11-13 by the session.
- **Rate limiting fails open.** When the storage cannot count a request, the request is let through unlimited, with a warning logged once per outage and an info line when Redis answers again, except on fail-closed endpoints (next entry). "Cannot count" is: the shared client is not connected (Redis is then not called at all, so the request loses no time), Redis errors or answers unexpectedly, or a connected Redis does not answer within 500 ms. The same rule covers the pre-routing limit. The trade-off: while Redis is down nobody is rate limited, so a flood in that window reaches the API. Failing closed would turn a Redis outage into a full API outage, health excepted, for every customer, during exactly the failures (Eid peaks) when the platform is under most strain. Redis being down already shows in readiness and the logs. Decided 2026-11-13 by the backend owner (step seven brief); the timeout by the session.
  - **Correction (foundation review, batch B).** This entry claimed "the 500 ms bound keeps a slow Redis from slowing every request". It did the opposite while Redis was down: every request waited the full 500 ms, because the shared client held each command while reconnecting (the review measured 500 to 516 ms per request), and the e2e test hid it by giving the storage a client with test-only options. Now the storage checks the client's status first and skips Redis at once when it is not `ready`; the 500 ms applies only to a connected Redis that is slow. Tested with the production client class and options, Redis stopped mid-test: ten requests took 3 to 23 ms each.
- **Sensitive endpoints fail closed.** `@RateLimit({ ..., failClosed: true })` makes an endpoint answer 503 SERVICE_UNAVAILABLE while the rate limit storage is unavailable, instead of letting requests through unlimited. OTP endpoints use it, and so does any endpoint where an unlimited request costs money or is a security risk. Why: each OTP request sends an SMS, which costs money per message, so an unlimited window during a Redis outage is a direct bill and an SMS-pumping target; a 503 on OTP only delays logins while the rest of the API stays up. The default stays fail open. Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **Named rate limit counters.** Every `@RateLimit` names its counter (`otp-request`); the key is the name and the client address, not the class and method, which let two controllers with the same class name share one counter by accident (finding 7). Endpoints share a counter only by declaring the same name with the same settings; the same name with other settings, or a method `@RateLimit` under a class-level `@SkipRateLimit`, stops the application at startup (`RateLimitPolicyCheck`), naming the endpoints. Settings are validated when the file loads: positive whole numbers, and a block never shorter than the window. Decided 2026-11-13 by the backend owner (foundation review, batch B); the name format and the startup check through Nest's DiscoveryService by the session.
- **Blocking keeps the counter.** The rate limit script no longer deletes the counter when it blocks a client, so a client whose block ends inside the window is still over the limit and is blocked again by its next request (finding 6: OTP with a 1 minute block in a 10 minute window allowed about 50 requests instead of 5). Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **Rate limit keys carry a cluster hash tag.** `jazla:rate-limit:{<sha256>}:hits` and `:blocked`: only the part in braces decides the Redis Cluster slot, so the script that touches both keys does not fail with CROSSSLOT on cluster-mode Redis (finding 9). Counters written under the old key format are ignored and expire with their window. Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **A rate limit before routing.** Guards run only on matched routes, so unknown routes and malformed bodies were never limited (finding 10). `PreRoutingRateLimiter`, Express middleware in `configureHttpApp` ahead of the body parser, counts every request per address: `RATE_LIMIT_PRE_ROUTING_MAX_REQUESTS` (default 600, twice the per-route default, so the per-route limit with its headers is what a normal client meets first) per `RATE_LIMIT_WINDOW_MS`, on its own counter (`pre-routing`), same storage, fails open. The health checks are not counted. Decided 2026-11-13 by the backend owner (foundation review, batch B); the default and the shared window by the session.
- **Request bodies.** JSON only (`application/json` and `application/*+json`), up to `REQUEST_BODY_LIMIT_KB`, default 100, registered explicitly (`bodyParser: false` at creation, then `useBodyParser`). Any other body type gets 415 UNSUPPORTED_MEDIA_TYPE (`requireJsonBody`). The form parser was removed: nested form bodies were accepted on every route, and a form is what a cross-site page can POST without a CORS preflight. A route that needs another type later enables its own parser for its path only. Files go to object storage through presigned uploads, never through the API. Decided 2026-11-13 by the backend owner (step seven brief; JSON only in the foundation review, batch B); the 415 check by the session.
  - **Correction (issue #229).** `requireJsonBody` refused a bodyless POST (`Content-Length: 0`, no Content-Type, what Node's client and browsers send), contrary to its own comment: type-is counts `Content-Length: 0` as a body. A request now has a body only with a Content-Length above 0 or a Transfer-Encoding (a chunked body counts even if empty: its length is unknown until read); a bodyless request passes whatever its type. Proven by `test/http-security.e2e-spec.ts` (fails with the old check). Decided 2026-11-14 by the backend owner.
- **The request logger runs first.** `configureHttpApp` mounts the pino-http middleware ahead of helmet, CORS, the pre-routing limit and the body parser, on every path, so a malformed, oversized or unsupported body and a request refused before routing are logged with their request id (finding 10). nestjs-pino mounted it at `init()`, after the parser and only under `/v1`; it now runs with `useExisting` and logs through a child of the request logger's pino instance, so there is still one instance and one destination. Decided 2026-11-13 by the backend owner (foundation review, batch B: parsers after the logger); the mechanism by the session.
- **Error filter edge cases.** When the response has already started (headers sent), the filter only sets the error for the request log and ends the response: no body can follow, and writing one threw inside the filter, losing the error and leaving the client waiting (finding 11). An HttpException with a status below 400 is not an error status, so it becomes INTERNAL_ERROR 500. A thrown value that is not an Error is logged as `NonErrorThrownError` describing it (a primitive's value, an object's property names only). Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **Readiness answers 503 from the start of shutdown** (`draining: true` in the body), so the load balancer stops sending new requests while workers drain for up to 25 s. The flag is set by a SIGTERM/SIGINT listener, before Nest runs any shutdown hook, because the order of `onModuleDestroy` across modules at the same depth is not something to rely on; `onModuleDestroy` sets it too, for a close without a signal. Liveness stays 200. Decided 2026-11-13 by the backend owner (foundation review, batch B); the signal listener by the session.
- **Guard order.** A global authentication guard must run after the rate limits, so failed token attempts are counted. The pre-routing limit is Express middleware and runs before every guard by construction; for the per-route limit, the authentication guard's `APP_GUARD` is registered in a module imported after `RateLimitModule`, and its task adds an e2e test proving 429 under repeated bad tokens (`.claude/rules/http.md`, "Guard order"). Decided 2026-11-13 by the backend owner (foundation review, batch B); the enforcement by the session.

### Integrations

- **Shape.** `src/integrations/<capability>/` holds a port (interface + injection token), types, errors, service, module, an `index.ts` public entry, and `providers/` with one file per vendor plus a fake. The folder and the word are "provider" (`resend.provider.ts`). Why *(inferred)*: one shape and one word, so any integration can be read by someone who has seen one.
- **List.** mail, sms, push, payments, storage, delivery, zatca, bnpl.
- **mail, sms, push.** An ordered provider list with fallback on retryable failures. An undocumented vendor error counts as retryable for these three. Why *(inferred)*: a message that is not sent costs more than a second attempt through another vendor.
- **payments.** Never fails over. One active provider takes new payments, each payment record stores its provider, and capture, void and refund go to that provider. An unknown or ambiguous gateway response marks the payment pending and triggers a status query. Why: a blind retry can charge the customer twice.
- **delivery and bnpl.** Like payments: the provider is recorded on the shipment or transaction, and every later call goes to that provider. No automatic failover.
- **zatca.** No fallback. Submissions go through a queue and retry against the same provider, with an idempotency key. Why: an invoice must never be submitted twice.
- **storage.** One provider, no fallback.
- **Test-only entry: `testing.ts` (R22).** Each integration has a second public entry, `testing.ts`, exporting its fake and test helpers; `index.ts` exports nothing test-only. Lint rule R22 refuses `testing.ts` from every source file except unit tests (`*.spec.ts`), the integration's own code included; `test/` is outside the boundary rules. Why: when the fake was exported from `index.ts`, production code could inject it with no rule to stop it. Decided 2026-11-14 by the backend owner (issue #229 corrections); the rule's mechanism (a policy dropped for spec files) by the session.
- **Storage, as built (issue #229).** The reference integration (REGISTRY.md). Decided 2026-11-14 by the backend owner (task brief) unless marked *session*:
  - **Two buckets**, public and private, separated by bucket, never by path. Public objects get `STORAGE_PUBLIC_BASE_URL/<key>` (later a CDN); private ones only a presigned GET created on request.
  - **Presigned POST for uploads**, never PUT: the policy carries `content-length-range` and the exact Content-Type, which the storage enforces; a presigned PUT cannot limit size. The API never streams file contents.
  - **Keys are the server's**: `<purpose with dots as slashes>/<yyyy>/<mm>/<dd>/<media id>` (UTC date). The client's file name is sanitised display metadata (`sanitizeFileName`), never part of a key.
  - **Request, upload, confirm.** Confirm checks existence, size, and the real type from the first bytes (`detectContentType`); the declared Content-Type is not trusted. A failure deletes the object, then marks the row rejected with a reason. *Session:* a real type that is allowed but differs from the declared one is rejected too (CONTENT_TYPE_MISMATCH), because the storage serves the declared type with the file; a missing object at confirm is a rejection (OBJECT_MISSING), as the brief lists existence among the checks.
  - **SDK.** `@aws-sdk/client-s3`, `@aws-sdk/s3-presigned-post`, `@aws-sdk/s3-request-presigner` 3.1159.0, pinned exactly (*session*: the newest release at least two weeks old). Connection timeout 3 s and request timeout 10 s (`throwOnRequestTimeout`), because the SDK sets none; the SDK's own 3 attempts stay.
  - **Error mapping** (*session*). Every failure becomes `StorageError` with a `reason` and `retryable`: unavailable and throttled are retryable (SERVICE_UNAVAILABLE); access-denied, bucket-missing, object-archived and rejected are not (INTERNAL_ERROR); neither is the client's fault. A missing object is a result (null), not an error. The codes come from the `@throws` of each SDK command and the SDK's retry classification (`@smithy/core`), not from memory; HeadObject's 404 has no body, so a missing bucket reads as a missing object there.
  - **Upload purposes.** Two declared as examples, `catalog.product-image` (public, JPEG/PNG/WebP, 5 MB) and `vendor.document` (private, PDF/JPEG/PNG, 10 MB), in `UPLOAD_PURPOSES` in the media module (*session*: a lookup table that other modules extend, like QUEUE_NAMES, so purposes are typed and found in one place).
  - **Cleanup** (*session* for the mechanism). A BullMQ job scheduler (`keepJobScheduled`, every MEDIA_CLEANUP_INTERVAL_SECONDS) runs `MediaService.removeExpiredUploads`: one conditional update claims every expired pending row (rejected, EXPIRED), then each claimed row's object and then row are deleted. Idempotent and safe beside a concurrent run or a confirmation; a confirmation of a claimed row gets MEDIA_UPLOAD_EXPIRED. MEDIA_PENDING_UPLOAD_TTL_SECONDS must exceed the upload URL's expiry (schema).
  - **Local MinIO** (*session*). The official `minio/minio` image is no longer published; Chainguard's free MinIO build is used, pinned by digest. Bucket setup runs in the MinIO container's entrypoint, not a one-shot service, because `docker compose up --wait` fails when any container exits. MinIO does not implement per-bucket CORS (PutBucketCors: NotImplemented), so CORS is server-wide (`MINIO_API_CORS_ALLOW_ORIGIN`, localhost origins). **Per-bucket CORS is required of the production storage provider** (decided 2026-11-14 by the backend owner): browsers upload straight to the buckets with presigned POSTs, and each bucket must allow exactly the app origins it serves; a provider that, like MinIO, offers only server-wide CORS is not acceptable for production. Public buckets allow anonymous `s3:GetObject` only: mc's `download` preset also allows listing every key. The e2e tests use the `-test` buckets (`scripts/e2e.mjs`).
  - **No endpoints yet**: an unauthenticated upload endpoint would be abusable; the e2e tests use a controller in `test/support/`.

### Code rules

- **Type safety.** `any` and `@ts-ignore` are never allowed.
- **Errors.** `AppError` and the error code list live in `src/common/errors/`. Codes are UPPER_SNAKE_CASE. Business code throws `AppError` or a subclass, never a raw `Error` or a Nest `HttpException`. Codes are a contract with the mobile app: once released, never renamed or reused.
- **Money helper.** `src/common/money/`. Clients receive integer halalas. No shared package.
- **Append-only finance ledger.** Every movement of money (customer payment, commission, merchant payable, refund, COD receivable from the delivery company, transfer) is a ledger entry. Entries are never updated or deleted; a correction is a new entry. Why: statements and settlements must be reproducible from the entries alone.
- **Configuration.** `@nestjs/config` loads `.env` files; a zod schema (`src/config/env.schema.ts`) validates the environment once, in `src/config/load-env.ts`, the only file that reads `process.env` (R11). The typed namespaces (`registerAs`: `app`, `logger`, `database`, `redis`, `queue`, `http`, `rateLimit`, `storage`, `media`) share that one result. `main.ts` waits for `ConfigModule.envVariablesLoaded` and calls `loadEnv()` before creating the app, so an invalid environment prints only one line per offending variable (what was expected, never the value) and exits with code 1, with no Nest log before it. `NODE_ENV` defaults to `development`. Decided 2026-11-13; the single validation and the clean exit replaced the first version the same day.
- **Error responses.** `{ code, message, details?, requestId }`, status in the status line, written only by the global `AllExceptionsFilter`. Messages come from one catalogue in Arabic and English; English only when `Accept-Language` ranks it above Arabic. No i18n library. Decided 2026-11-13.
- **Mapping Nest exceptions.** An HttpException gets the code for its status: 400 BAD_REQUEST, 401 UNAUTHORIZED, 403 FORBIDDEN, 404 NOT_FOUND, 405 METHOD_NOT_ALLOWED, 409 CONFLICT, 413 PAYLOAD_TOO_LARGE, 415 UNSUPPORTED_MEDIA_TYPE, 429 RATE_LIMITED. Another 4xx keeps its status with BAD_REQUEST, another 5xx keeps its status with INTERNAL_ERROR. VALIDATION_FAILED is produced only by the validation pipe, because clients read it as "the input was wrong". Malformed JSON is BAD_REQUEST. The exception's own message is never sent. Decided 2026-11-13 by the backend owner, replacing the session's first mapping.
- **Pretty logs only when available.** pino-pretty (a dev dependency) is used only when `NODE_ENV` is development and the package resolves; otherwise logs are JSON. Decided 2026-11-13.
- **Validation details.** `details` of VALIDATION_FAILED is `[{ field, constraints }]`: dotted field paths and class-validator constraint names (`isInt`, `whitelistValidation`), not messages, so they are stable and language-neutral. Decided 2026-11-13 by the session.
- **Request ids.** The incoming `x-request-id` is reused when it is at most 128 characters of `A-Z a-z 0-9 . _ : -`, otherwise replaced by a UUID. Decided 2026-11-13 by the session. Why: reusing a client's id ties its logs to ours; the limits stop log injection and oversized values.
- **Logging.** pino through nestjs-pino. One line per completed request: info, warn for 4xx, error for 5xx with the original error (the filter hands it to the logger as `response.err`). Readable through pino-pretty in development, JSON in production, silent in test. What a line may hold is decided by allowlists, in one place (`createLoggerParams`): errors keep name, message, code, stack and cause only (ioredis put the Redis password in `err.command`, Prisma whole rows in `err.meta`); requests are logged with the path only (no query string), `req.ip` and allowlisted headers; secret-like fields are redacted at any depth, case-insensitively, by walking each line in `formatters.log`, because pino's path-based `redact` matches exact, case-sensitive paths only. A Prisma error (any `PrismaClient*` class) is logged with its class name, code, model (`meta.modelName`) and stack frames, and a fixed message in place of its own: a validation error prints the query with its argument values, a phone number among them. Decided 2026-11-13; the allowlists replaced path redaction the same day (foundation review, batch A); the Prisma message in batch B.
- **e2e coverage.** An e2e test covers every case that applies to its endpoint among success, invalid input, authentication and ownership. Decided 2026-11-13.
- **Kept additions.** Confirmation before destructive schema changes, a module reads only its own tables, the `ASSUMPTION:` comment convention, the time helper and the masking helper.
