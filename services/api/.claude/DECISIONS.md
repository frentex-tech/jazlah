# Decisions and open questions (JAZLA API)

Two lists. **Open questions** are things nobody has decided: do not guess them, ask. The **decisions in force** are what has been decided, so the next session does not decide it again differently.

Paths are relative to `services/api/`.

## How to use this file

- Your task depends on an open question: stop and ask the user. If they tell you to proceed anyway, put the assumption behind an interface or a config value, mark it in the code with a comment that starts `ASSUMPTION:`, and list it in your report.
- The user answers an open question: delete the row and add a line to the decisions.
- You make an architectural decision while working (a new shared building block, a new convention, a new dependency the user approved, a pattern the next module should copy): add a dated line under the right heading in the same change, update the rule file it affects, and update `.claude/ARCHITECTURE.md` if it changes the layout. A decision that lives only in a chat transcript will be made again, differently.
- A decision listed here is changed only by the backend owner. If you think one is wrong, say so in your report.

## Decisions in force

A reason marked *(inferred)* was not given by the person who decided; it is the recording session's reading.

### Project and platform

- **Standalone project.** `services/api/` has its own `package.json` and lockfile. No workspace and no Turborepo. Decided 2026-11-13. Why: the build proceeds one small step at a time, and the API must stand on its own.
- **Source of truth.** Stated once, at the top of `CLAUDE.md`. Decided 2026-11-13.
- **Stack.** NestJS 12, TypeScript 6 `strict`, Jest, ESLint 10 with typescript-eslint, pnpm. Decided 2026-11-13, replacing NestJS 11, TypeScript 5 and ESLint 9. Why: Nest 11 would have pinned Swagger to an old major from its first day, and ESLint 9 reached end of life on 2026-08-06. TypeScript stays on 6 because ts-jest, typescript-eslint and the Nest tooling do not accept TypeScript 7.
- **CommonJS.** The project compiles to CommonJS (`module: nodenext` with no `"type": "module"`); Nest 12's ESM-only packages are loaded through Node's `require(esm)`. Decided 2026-11-13. Why: the Nest 12 CommonJS template keeps Jest and the existing path aliases unchanged, while the ESM template moves to Vitest. Moving to ESM later is its own step.
- **Node 26.** `engines.node >=26`, `@types/node ^26`, `.nvmrc` 26. Decided 2026-11-13, replacing Node 24. Why: Node 26 was the current LTS when the project started (LTS from 2026-10-28, supported until 2029-04-30).
- **Linting is ESLint, not oxlint.** The Nest 12 template generates oxlint; this project keeps ESLint 10 because the planned folder boundary rules are written as ESLint rules. Decided 2026-11-13.
- **Database.** PostgreSQL 17 with PostGIS, through Prisma with a multi-file schema, one schema file per domain. Local image `postgis/postgis:17-3.5`. Why *(inferred)*: PostGIS is needed for coverage polygons, and each domain owns the file that holds its models.
- **Prisma 7.10.1, pinned exactly.** `prisma`, `@prisma/client` and `@prisma/adapter-pg` at 7.10.1: npm's `latest` tag points to an 8.0 release candidate. The `prisma-client` generator emits CommonJS (`moduleFormat = "cjs"`, bare imports) into `src/infra/database/generated/prisma/` (gitignored, not linted, skipped by the registry check); PostgreSQL is reached through the pg driver adapter with a 5 s connection timeout; `prisma.config.ts` holds the URL and loads `.env` with dotenv. Decided 2026-11-13.
- **Local database.** `docker-compose.yml` runs `postgis/postgis:17-3.5` with databases `jazla` and `jazla_test`, on host port `JAZLA_DB_PORT`, default 5434, because 5432 and 5433 were taken on the first machine. e2e tests use `jazla_test`, derived from `DATABASE_URL` by `scripts/e2e.mjs` (database name + `_test`), which applies migrations first. Decided 2026-11-13 by the session.
- **PostGIS is enabled by the first migration** (`CREATE EXTENSION IF NOT EXISTS postgis`, added by hand). Prisma 7 leaves the extension's objects alone: `prisma migrate diff` against a PostGIS database reports no change. Decided 2026-11-13.
- **Readiness.** `GET /v1/health` is liveness and touches nothing; `GET /v1/health/ready` checks each dependency in parallel (the database with `SELECT 1` and Redis with `PING`, 1 s timeout each) and answers `{ status, checks }` with 200 or 503, not the error shape, so 200 and 503 have one shape. The failure is logged, never returned. Decided 2026-11-13 by the session.
  - **Redis on the right database (foundation review, batch B).** The Redis check sends `CLIENT INFO` instead of `PING` and reports Redis down when the connection is not on the database `REDIS_URL` names. Why: when Redis refuses the database (SELECT fails: fewer databases on the server, or cluster mode), ioredis emits an error, then becomes ready on database 0 and answers PING (checked against ioredis 6.0.0 and the local Redis 7), so the API would use another environment's data while readiness said up. `REDIS_URL` itself now accepts only databases 0 to 15 and only the lowercase `redis://` and `rediss://` schemes (`REDISS://` passed the check, which lowercases, but ioredis then connected without TLS). Decided 2026-11-13 by the backend owner (foundation review, batch B); CLIENT INFO as the means by the session.
- **Prisma conflict details.** With the pg adapter, Prisma 7 reports a unique violation by constraint name, not its fields. CONFLICT `details` is `{ constraint, fields? }`: fields for a primary key (`['id']`, by convention) and when the driver reports them. Resolving other constraint names to fields would need a catalog lookup; not built. Decided 2026-11-13 by the session.
- **Unique constraints become specific error codes in the repository.** A repository matches the constraint names it knows (named explicitly in the schema, `<table>_<columns>_key`) and throws a specific code (for example PHONE_ALREADY_REGISTERED); `mapPrismaError`'s generic CONFLICT is the fallback for the rest. No catalog lookup. Decided 2026-11-13 by the backend owner (step five brief). Rules 12a and 17a in `.claude/rules/database.md`.
- **Redis 7 with BullMQ.** Versions pinned exactly: `bullmq` 6.7.6 (npm `latest`), `@nestjs/bullmq` 12.0.2, `ioredis` 6.0.0 (the version BullMQ 6.7.6 is built and tested against; an optional peer of BullMQ 6). Decided 2026-11-13 by the session.
- **Local Redis.** `docker-compose.yml` runs `redis:7-alpine` with an append-only file (fsync every second), `maxmemory-policy noeviction` (BullMQ requires it) and a named volume, on host port `JAZLA_REDIS_PORT`, default 6380, because 6379 was taken on the first machine. `pnpm infra:up` / `infra:down` manage both services; `db:up` / `db:down` were removed (nothing depended on them). e2e runs use the next logical Redis database (`/0` → `/1`), derived by `scripts/e2e.mjs`, and remove their queues afterwards. Decided 2026-11-13 by the session.
- **One shared Redis client, BullMQ's own connections.** `RedisService` (ioredis) is for general use; BullMQ opens its own connections from `{ url: REDIS_URL }` for every queue and worker, as its documentation recommends (workers need `maxRetriesPerRequest: null`). Decided 2026-11-13 by the backend owner (step five brief).
  - **Correction (foundation review, batch B): neither fails fast.** This entry said the shared client "fails a command fast while Redis is down" and that "producers fail fast". Both were wrong. The shared client (`maxRetriesPerRequest: 1`, offline queue on) holds a command while it reconnects; the review measured each rate limit call waiting the full 500 ms timeout. Producer connections keep ioredis's defaults (20 retries with BullMQ's backoff), so `queue.add` against an unreachable Redis was still pending after 60 s. Code that must not wait checks `status === 'ready'` or bounds the call with `withTimeout`; the rate limit storage does both.
  - **Producers now fail fast (foundation review, batch C).** Every registered queue is a `BoundedQueue` (`src/infra/queue/bounded-queue.ts`, set as @nestjs/bullmq's queue class by `QueueRegistrationModule`, so R15 covers every queue): `add` and `addBulk` check the queue's own connection and refuse at once with SERVICE_UNAVAILABLE (503) while it is not `ready`, and bound the add to `QUEUE_ADD_TIMEOUT_MS` (500 ms) while connecting or when Redis is slow. Measured with Redis stopped behind a TCP proxy (`test/queue.e2e-spec.ts`): five adds answered 503 in 500.9 ms, 0.1 ms, 0.0 ms, 0.0 ms and 0.0 ms. The first waits the 500 ms because the client still reports `ready` until it notices the dropped socket; that add was sent, so it may still land when Redis returns, which is why a retried add uses `buildJobId`. Before the change, the same add was still pending after 3 s (measured) and the earlier review measured over 60 s. Why the status check rather than `enableOfflineQueue: false` on the queue connection: @nestjs/bullmq gives each worker its queue's connection options, and the workers must keep waiting for Redis. Decided 2026-11-14 by the backend owner (foundation review, batch C); the mechanism by the session.
  - **Observed, not fixed: BullMQ 6.7.6 workers can hang in `close()` after their connection dropped and came back**, with the client `ready` again (seen twice in the producer test while the app's workers shared the proxied connection; the producer test now runs without processors). If it happens in production, shutdown waits for the orchestrator's SIGKILL. Not investigated further in batch C.
- **Queue folder is `src/infra/queue/`**, replacing the `src/infra/jobs/` named earlier. Decided 2026-11-13 by the backend owner (step five brief).
- **Queue registration with an error listener.** Every queue is registered with `QueueRegistrationModule.register`, which sends queue `error` events to the logger at warn; lint rule R15 refuses `BullModule.registerQueue` outside `src/infra/queue/`. Decided 2026-11-13 by the backend owner (step six brief).
- **Deterministic job ids stop duplicate enqueues, not duplicate work.** `buildJobId` makes BullMQ ignore an add while a job with that id is waiting, delayed, active, or kept after it ended (completed: 1 day, at most 1,000; failed: 14 days). A failed job blocks re-adding until it is removed; once removed, the id enqueues again; retries, stalled jobs and shutdown cancellations run the same job again. Work that must happen exactly once records an idempotency key in the database inside the transaction that does the work: `IdempotencyRunner.runOnce(operation, key, work)` over the table `idempotency_keys` (unique `idempotency_keys_operation_key_key`). It claims the key with `INSERT ... ON CONFLICT DO NOTHING` (Prisma `createMany` with `skipDuplicates`) before the work, so a concurrent run waits on the unique index and then returns the stored result; the result is stored as JSON and returned to every repeat; work that throws deletes the claim. Decided 2026-11-14 by the backend owner (foundation review, batch C, finding 17); the claim-first design, the `{ value }` outcome and the table's columns by the session.
- **Job logging on the worker's events.** `JobProcessor` intercepts @nestjs/bullmq's assignment of `_worker` and attaches `JobLifecycleLogger` to the worker's `active`, `completed`, `failed` and `stalled` events, plus the error listener and the shutdown timer. Why: logging inside `process` (as before) missed the final failure of a stalled job (BullMQ fails it in the worker without calling the processor), logged BullMQ's control-flow errors (DelayedError, WaitingChildrenError, RateLimitError) as failures, logged "completed" before BullMQ stored the completion, and a subclass overriding `onApplicationBootstrap` dropped the listeners. Lint rule R17 keeps WorkerHost, QueueEvents and FlowProducer (and their @nestjs/bullmq helpers) inside `src/infra/queue/`; R18 forbids a processor from defining `process` or `_worker`. Processors must be safe to run beside a retry of themselves. Decided 2026-11-14 by the backend owner (foundation review, batch C, findings 18 to 20); intercepting `_worker` and forbidding QueueEvents and FlowProducer (rather than wrapping them) by the session.
- **Event bus.** `@nestjs/event-emitter` 12.0.3, pinned exactly, wrapped in `src/infra/event-bus/` (only importer: lint rule R16). Events are `DomainEvent<'domain.entity.action'>` classes with a static `eventName`; subscribers name the class (`@OnDomainEvent`), so the compiler rejects a non-event and a wrong payload. Subscribers run asynchronously (`setImmediate`), and their errors are logged with the event and subscriber names. Decided 2026-11-13 by the backend owner (step six brief); the typing approach by the session.
  - **Correction and change (foundation review, batch C, findings 22 and 23).** `DomainEvent` and its types moved to `src/common/events/`, plain TypeScript, so a module's `domain/` can extend it under R8 (it was in `src/infra/`, which `domain/` may not import). The comments claimed the bus refused a class whose static name differed from its type; only `@OnDomainEvent` checked that, and `publish(event)` checked nothing about the class (a type cannot reach an instance's constructor). `publish` now takes the class too, `publish(OrderPlacedEvent, event)`, typed with `DomainEventClass`, so a non-event, a class without a static name, a mismatched name and an event under another class's name do not compile (`test/types/event-bus.type-test.ts`); a run-time check still guards casts. Decided 2026-11-14 by the backend owner (batch C); passing the class by the session.
- **Ambient transactions.** The open transaction lives in the AsyncLocalStorage scope. Repositories and CRUD services query through `DbContext.client` (the scope's transaction client, or the root client outside one); use cases open transactions with `TransactionRunner.run`. `runInTransaction` called inside a scope joins it whatever client it is given; an independent transaction from inside one is not supported. `DbClient` parameters were removed. Decided 2026-11-13 by the backend owner (foundation review, batch A), replacing the client passed down by hand, which let a root client inside a transaction open a second, independent one.
- **A database error ends the transaction.** A Prisma query extension (`trackQueryFailures`) marks the scope failed when any query in it fails; if the work then returns normally, `runInTransaction` rolls back and rejects with TransactionAbortedError (INTERNAL_ERROR), dropping after-commit callbacks. Strict on purpose: even an expected failure, such as `findUniqueOrThrow` finding nothing, ends the transaction; use `findUnique`, `upsert` or `ON CONFLICT`. Decided 2026-11-13 by the backend owner (foundation review, batch A); the extension as the mechanism by the session.
- **No external I/O inside a transaction**, and write conflicts are retried: P2034 reruns the transaction up to 3 times with full-jitter delays (25 ms base, doubling), then TRANSACTION_CONFLICT (409). Decided 2026-11-13 by the backend owner (foundation review, batch A); the attempt count and delays by the session.
- **Database pool and transaction defaults are config**: DATABASE_POOL_SIZE 10, DATABASE_CONNECTION_TIMEOUT_MS 5000, DATABASE_TRANSACTION_TIMEOUT_MS 5000, DATABASE_TRANSACTION_MAX_WAIT_MS 2000, DATABASE_ISOLATION_LEVEL ReadCommitted (Prisma's and pg's previous implicit defaults, now stated). Decided 2026-11-13 (foundation review, batch A).
- **Database errors mapped.** P2007, P2000 and P2020 to BAD_REQUEST; P2010 by its driver error kind; P2028 and an unreachable or overloaded database (P1001, P1008, P1017, P2037, pg's connection timeout) to the new SERVICE_UNAVAILABLE (503); P2034 to the new TRANSACTION_CONFLICT (409); check and exclusion violations to CONFLICT. Prisma reports those as P2039, its code for any unclassified PostgreSQL error, so only SQLSTATE 23514 and 23P01 are mapped and every other P2039 stays INTERNAL_ERROR. Decided 2026-11-13 by the backend owner (foundation review, batch A); P2020 and the P2039 narrowing by the session.
- **Events wait for the commit.** `runInTransaction` keeps an after-commit list in AsyncLocalStorage; `EventPublisher` adds to it through `runAfterCommit`. Delivered after the outermost commit, dropped on rollback, dispatched at once outside a transaction. Decided 2026-11-13.
  - **The scope has a state (foundation review, batch C, finding 21).** `TransactionScope.state` is `open`, then `committed` or `rolled-back`. Async work started inside a transaction keeps its scope after it ends; before, a callback it registered was pushed onto a list that had already run and was silently lost. Now it runs at once after a commit, and is dropped with a warn after a rollback. Every callback runs isolated (`runIsolatedCallback`), outside a transaction too: a throw or a rejected promise is logged at error and stops neither the caller nor the other callbacks (a throw outside a transaction used to reach the caller, and a rejected promise was unhandled). Decided 2026-11-14 by the backend owner (batch C).
- **runInTransaction joins by scope.** Corrects step four: Prisma 7 transaction clients have `$transaction`, so the shape test (`'$transaction' in client`) never joined and a nested call opened a nested transaction. It now joins when given the transaction client of the scope it runs in. Decided 2026-11-13 by the session.
- **Events only for losable effects.** Notifications, realtime updates, cache invalidation. An effect that must happen goes through a job with a deterministic id. Ledger entries are written in the same transaction through the finance module's service. **Planned:** a transactional outbox for payment webhooks, built with the payments module. Decided 2026-11-13 by the backend owner (step six brief).
- **Bounded worker shutdown.** `@nestjs/bullmq` closes workers in `onModuleDestroy` and waits without limit. `JobProcessor` starts a 25 s timer when its worker starts closing; when it ends, the active jobs' abort signals fire and the jobs end with `JobCancelledError`, so BullMQ retries them later. The database and Redis clients close in `onApplicationShutdown`, after the workers, so a finishing job can still use them (PrismaService moved there from `onModuleDestroy`). Decided 2026-11-13 by the session.
- **Workers by role.** Production runs API processes and worker processes separately, from the same build: `QUEUE_WORKERS_ENABLED` is false for an API process and true for a worker process. Why: job load at peak times (Eid al-Adha) must not slow down API responses; a worker process is scaled on its own, and an API process spends no CPU or connections on jobs. The variable is required in production (no default, startup fails without it, as for TRUST_PROXY_HOPS) and true elsewhere when unset, so a developer's single process runs everything. Processors and schedulers are provided through `provideWorkers` (`src/infra/queue/`), which, when off, provides an inert object instead: @nestjs/bullmq finds processors by the class of each provider's instance and Nest runs lifecycle hooks on that instance, so no worker connection opens and nothing is scheduled; queues and producers work as usual. e2e apps start with workers off (`scripts/e2e.mjs`) and a suite turns on only the worker it needs (`workers: [...]`, an `overrideProvider(X).useClass(X)`), which removed the list of module processors `createQueueProbeApp` had to keep. Decided 2026-11-14 by the backend owner (issue #229 corrections); the variable name and the factory mechanism by the session.

- **Staging database and Redis outside Render (issue #8).** The owner created PostgreSQL on Neon and Redis on Upstash (both free, Frankfurt; Upstash over TLS), so `render.yaml` runs only the two web services: `DATABASE_URL` and `REDIS_URL` are typed in Render (`sync: false`). This replaces the free Render Postgres and Key Value of the entry above, and with them the 30-day expiry and the 25 MB, non-persisted Redis. `DATABASE_URL` is Neon's direct string (no `-pooler`): `prisma migrate deploy` runs at start with the same URL, and migrations need a session connection, not PgBouncer's transaction mode. Neon's compute sleeps after 5 minutes and wakes in up to a few seconds, so staging sets `DATABASE_CONNECTION_TIMEOUT_MS=15000`. Neon free (checked 2026-11-21, neon.com/pricing): 1 GB, 100 CU-hours a month (about 400 hours at 0.25 CU), never expires; PostGIS and pg_trgm are available. **Queue workers are off on staging** (`QUEUE_WORKERS_ENABLED=false`) because Upstash free allows 500,000 commands a month, and Upstash bills a Lua script as one command plus one per `redis.call` inside it (upstash.com/docs/redis/overall/billing). Counted from BullMQ 6.7.6's source for one idle worker: the main loop blocks on `BZPOPMIN` for at most 10 seconds (hard-coded `maximumBlockTimeout`), then runs `moveToActive` (6 calls): 8 commands every 10 s. The media-cleanup job scheduler always holds a delayed job, so the loop is capped at 10 s and `drainDelay` (used only when nothing is delayed) changes nothing. The stalled check (`moveStalledJobsToWait`, 6 calls) adds 7 every `stalledInterval` (30 s). That is about 69,000 + 20,000 = 89,000 commands a day, the month's quota in under 6 days of awake time. A `stalledInterval` of 5 minutes saves only about 18,000 a day; the 10-second loop has no setting. Even the 15-minute sleep doesn't save it: 8 awake hours a day is about 900,000 a month. ### Shutdown

- **An overall shutdown deadline (foundation review, batch D).** `main.ts` closes the app on SIGTERM or SIGINT through `shutdownOnSignals` (`src/infra/shutdown/`) instead of Nest's `enableShutdownHooks`, which waits without limit. Past `SHUTDOWN_DEADLINE_MS` (default 28,000, range 1,000 to 29,000: under a typical 30 s grace period, above the 25 s jobs get) the process logs at error `stillClosing` (the resources that began closing and never finished: workers, queues, the database and Redis report themselves through `trackClosing`/`closingResources`) and exits with code 1. Why: BullMQ 6.7.6 workers were seen never to finish closing after a Redis reconnect, which would hold every deploy until the orchestrator's SIGKILL, with nothing logged. The timer keeps the process alive while the close runs (otherwise a close stuck on a promise with nothing else open exits with 0) and is unreferenced after a clean close. A clean close now exits with code 0 instead of re-raising the signal. Proven by `test/shutdown.e2e-spec.ts` (a child process with a resource that never closes: exit code 1, the log line naming it). Decided 2026-11-14 by the backend owner (batch D); the mechanism and the default by the session.

### Structure

- **Top-level folders.** `src/config`, `src/common`, `src/infra`, `src/integrations`, `src/modules`.
- **Infrastructure folder.** `src/infra/` holds health, the HTTP setup, API docs, rate limiting, database, queue, realtime, the event bus, redis and logger. Why *(inferred)*: one place for the infrastructure we run ourselves, apart from business code.
- **Health is infrastructure.** `src/infra/health/`, served at `GET /v1/health`. Decided 2026-11-13. Why: it will check the database and Redis in later steps.
- **Jobs.** `src/infra/queue/` holds the BullMQ connection, the default job options, the queue name list and the shared helpers only; each module registers its own queue. A processor that runs business logic lives inside the module that owns that logic. Why: `infra` must not import from `modules`. Payloads carry ids and processors are idempotent (`.claude/rules/modules.md`, "Jobs").
- **Realtime.** `src/infra/realtime/` holds the socket gateway, room conventions and a publishing port. Modules publish through the port and never import the gateway. Why: same.
- **Event bus.** Modules communicate through an in-process event bus. Publishers and subscribers both live in modules; the bus lives in `infra`. Why: this is how notifications, realtime updates and jobs react to orders without any import from `infra` into `modules`.
- **`auth` is a four-layer module**, added to `FOUR_LAYER_MODULES` (R14). Why: it holds real security rules (code expiry and attempts, refresh rotation, reuse detection), which belong in a domain layer that is tested without a framework. `users` stays CRUD-shaped. Every other module starts as controllers + service + dto and is promoted when it gains a state machine or money logic. Why *(inferred)*: layers where the rules justify them, and no empty layers elsewhere. A CRUD module may have one service per sub-resource when one class would have several reasons to change (backend owner, issue #239: `customers`).

### Authentication (issue #233)

- **A sign-in is scoped to one audience.** The OTP request and verify bodies carry the audience; the session and the access token carry exactly one, so an admin's token from the customer app has no admin power. Any user may sign in as a customer, and is created on the first successful customer verification. Vendor, kitchen and admin access is granted, never self-registered: table `user_access` (user, audience, organisation, `deactivated_at`), one access per user per audience.
- **`user_access.organisation_id`** had no foreign key until the vendors module (issue #235, below: it now references `vendors`). It is null exactly for admin, which two check constraints written by hand in the migration enforce together with "never customer" (`user_access_audience_check`, `user_access_organisation_check`). The kitchens' foreign key comes with their module.
- **A staff request for a phone without active access is indistinguishable from a real one.** Same response, no SMS, and a stored challenge whose hash no code matches, so the resend wait and the attempt counting are identical; verification fails as a wrong code. Staff requests answer without waiting for the SMS, so the response time does not reveal staff phones either: a failed send is logged at error and its row made unverifiable, never deleted, so it stays the newest and the resend wait applies exactly as for a phone without access, and an SMS outage reveals nothing (review of #234, fixed 2026-11-15; `TrackedDetachedWork`, which a shutdown waits for and names if it outlasts the deadline). Customer requests wait for the SMS and answer 503 when it fails. Why: a client must not be able to learn which phones are staff.
- **OTP rules.** A challenge belongs to a phone and an audience; only the newest can be verified, so a new code invalidates the previous one; a resend within AUTH_OTP_RESEND_WAIT_SECONDS (60) is RATE_LIMITED with Retry-After. An attempt is claimed, in its own committed statement, before the code is compared, so the limit holds under concurrent guesses and a wrong code cannot be rolled back. Codes accept Arabic-Indic and Extended Arabic-Indic digits, as phones do. Codes are stored as HMAC-SHA256 with AUTH_OTP_SECRET over phone, audience and code (*session*: a keyed hash, because any plain hash of a 6-digit code is reversed by trying them all).
- **Limits, all from configuration and all failing closed**: per address 30 requests and 30 verifications per 10 minutes; per phone and audience 3 requests per 10 minutes, each audience counted on its own so abuse of one cannot lock the phone out of another; and per phone 10 customer requests per day, the daily cap applying to the customer audience only, since it exists to bound SMS cost (changed 2026-11-15 by the backend owner, review of #234: the counters used to be shared across audiences, and the daily window blocked a staff phone for a day after about 11 requests by anyone who knew the number). Requests with and without staff access are counted identically: the limit is counted before access is looked up. **Remaining risk:** anyone requesting customer codes for a phone that is not theirs can exhaust that phone's daily customer cap, and its owner then cannot sign in as a customer until the day ends. **Planned before launch:** app attestation on the OTP request (App Attest on iOS, Play Integrity on Android), so only the genuine app can request codes. *Session:* the resend wait is read from the newest challenge, not counted atomically, so two simultaneous requests can both pass; the phone counters bound that (accepted by the backend owner). A refused resend does not count against the phone.
- **`@RateLimit` numbers may come from configuration.** `from: (limits) => limits.<name>` picks one of `rateLimit.configured`; the decorator stores a declaration, and the guard, the startup check and `RateLimiter` resolve it with one function (`resolveRateLimitPolicy`), at startup and per request, never when the file loads (the OpenAPI document is generated without configuration). One mechanism: the OTP address counters stay under the decorator, with its headers and startup check. `RateLimiter.consume(options, key)` is the same thing for a key the caller supplies; a phone reaches it only as an HMAC. Mechanism by the session.
- **Disabled users** (`users.disabled_at`) cannot verify or refresh. ACCOUNT_DISABLED is returned only after a correct code, at refresh and on `me`, never at request, so only the phone's owner can see it. Refresh also fails, and revokes the session (`access_lost`), when staff access was deactivated or moved to another organisation after sign-in.
- **Review accounts.** AUTH_REVIEW_ACCOUNTS lists phone numbers with fixed codes, empty by default; they never trigger an SMS and each sign-in with one is logged at warn. Why: Apple and Google require a working demo sign-in to approve the app. A review account on a staff audience still needs granted access, and is under the same limits as any phone.
- **Sessions and tokens.** A session stores the audience, the organisation, the device name and platform (ios, android, web) sent at verify, and a last-used time updated on refresh. The access token (HS256, 15 minutes) carries the user, the single audience, the organisation and the session. Signing keys have ids: a current secret and an optional previous one, the key id in the token header, so the key can be rotated without signing everyone out. Refresh tokens are 256 random bits stored as SHA-256, rotated on every use; a used token presented again revokes the session (strict reuse detection: a client that lost the answer to a refresh, or refreshes twice at once, signs in again).
- **The guard trusts the token alone: a 15-minute window.** After logout, logout-all or reuse detection, and after a user is disabled or staff access deactivated, an access token already issued works until it expires (AUTH_ACCESS_TOKEN_TTL_SECONDS, at most 15 minutes by default). Accepted: checking the session on every request would cost a read per request. Refresh refuses at once in each of those cases; verify refuses a disabled user; `me` refuses at once only a disabled (or deleted) user, because it reads the user, not the session or the access, so after logout or a deactivated access it still answers until the token expires (corrected 2026-11-15, review of #234).
- **Deny by default.** A route outside the five audience prefixes is denied unless marked `@Public()`; `/v1/health` and `/v1/health/ready` are marked, test controllers mark themselves, and the application refuses to start with an endpoint that has neither (`RouteAudienceCheck`). Nothing becomes public by omission.
- **Secrets.** AUTH_ACCESS_TOKEN_SECRET and AUTH_OTP_SECRET are required in production; elsewhere an unset one is random per process (*session*: no placeholder credential in the repository, no CI variable).
- **Error codes.** OTP_INVALID (422, not 401, so a client's refresh-on-401 logic does not fire), OTP_EXPIRED (410: no code can be verified, request a new one), REFRESH_TOKEN_INVALID (401: sign in again), ACCESS_TOKEN_EXPIRED (401: refresh), ACCOUNT_DISABLED (403).
- **`pnpm admin:create <phone>`** grants admin access, creating the user if needed; idempotent. It is how the first admin exists; no endpoint grants access yet.
- **Production deployment waits on a real SMS provider.** `AuthModule` imports `SmsModule`, which refuses to start with no provider, and `log` is refused in production; Msegat is blocked on its send-response documentation (below). Accepted for now.
- **Later task: cleanup of expired rows.** Nothing deletes expired `otp_challenges`, used or expired `refresh_tokens`, or ended `auth_sessions`. A scheduled job like media's is a task of its own.
- **Shared code changed for this** (*session*, accepted by the backend owner): `AppError` carries `retryAfterSeconds`, which the filter sends as Retry-After; the guard lives in `src/common/guards/` behind the `AccessTokenVerifier` interface in `src/common/auth/` (R1); `src/common/auth/` is plain TypeScript and was added to `DOMAIN_SAFE_COMMON`, so a module's `domain/` uses `Audience`, `StaffAudience` and `AuthenticatedUser` instead of redeclaring them (`StaffAudience` was declared twice, in auth and users, until the review of #234). `@nestjs/jwt` 12.0.3, pinned exactly (the newest release at least two weeks old).
- *Session:* **use cases take `Pick<TransactionRunner, 'run'>`** with `@Inject(TransactionRunner)`, so a unit test passes a plain object; the auth test kit's runner puts the in-memory repositories back when the work throws, so rollbacks are tested without a database.

Verify asks the same checker after a correct code (VENDOR_SUSPENDED, the code not consumed, so only the phone's owner learns it), refresh on every call (*session*: the session is revoked, `access_lost`, as for lost access; after reinstatement the user signs in again). - **Access is scoped by the token.** Every vendor-side repository call takes the vendor id from the token's organisation, applications the applicant from the token; another vendor's record is NOT_FOUND exactly like a missing one. A vendor changes only its logo, cover, descriptions, contact details and VAT number (*session*: FR-VND-02's location, hours and pickup come with their own tasks; #243 below). An admin changes any vendor's profile with the same rules, and the city, the logo uploaded by that admin, audited (`PATCH admin/vendors/:id/profile`, owner, review of #236): the platform vendor has no owner, so this is how its profile is set.
- **Media endpoints** (`customer/`, `vendor/`, `admin/` `media/uploads` and `media/:id/confirm`): each audience only its purposes (`AUDIENCE_UPLOAD_PURPOSES`), the file owned by the uploader, and another user's file answered as missing. New public `vendor.logo` purpose (*session*: JPEG, PNG or WebP up to 2 MB). Public URLs in bulk come from one database read without a storage call (`MediaService.getPublicUrls`).
  - *Session (issue #243):* new public purpose `catalog.category-image` (JPEG, PNG or WebP up to 2 MB, as `vendor.logo`), admin uploads only (Catalog, "Category images").
  - **Upload limits (review of #236).** Each upload costs storage, so the endpoints fail closed on named counters shared by the three audiences (`MEDIA_RATE_LIMITS`, *session* numbers): 30 upload requests and 60 confirmations a minute per address, and 100 upload requests an hour per user whatever the address (`RateLimiter` in `MediaService.requestUpload`). Confirmed files that nothing refers to are kept: their cleanup is a later task.

- **Lists** use keyset pagination with an opaque cursor, default 20, maximum 50, no total (`http.md`, "Lists"). *Session:* `src/common/pagination/` is plain TypeScript and was added to `DOMAIN_SAFE_COMMON`, so ports return `Page<T>`; its DTO and validator are in `src/common/dto/` and `src/common/decorators/`.

  - **Contact phone and email** on the vendor, nullable, set or cleared (null) by the vendor (`PATCH vendor/profile`) and an admin (`PATCH admin/vendors/:id/profile`, audited); returned to the vendor and admins, never on the public page. ### Catalog (issue #237)

Decided 2026-11-16 by the backend owner (task brief, `.claude/plans/catalog.md`) unless marked *session*.

- **Money first** (`src/common/money/`): an immutable amount of whole halalas; add, subtract, multiply by a whole quantity, sum, min, compare; half a halala rounds up. A split by basis points takes each part as the rounded running total minus the previous one (*session*), so the parts are never negative and always sum back. No VAT extraction yet.
- **`catalog` is a four-layer module** (`FOUR_LAYER_MODULES`). Why: a product's review is a state machine (`ProductStatusMachine`) and it carries prices.
- **The public queries join `vendors.status` read-only**: the one exception to "a module reads only its own tables". Vendor names and the platform vendor's id come through the vendors module's export `VendorDirectory`, not a join (*session*).
- **Admin lists** (categories, meat types, cutting styles, "without" items): one table each with the same columns (bilingual name, active flag), served by one repository and one set of use cases taking the list (`admin/lists/:list`; *session*). An inactive entry cannot be chosen any more; an inactive category hides its products. List changes are not audited (*session*). Categories have a display order admins set (`sort_order`, 0 by default, never negative; backend owner, review of #238): set on create or update, refused on the other lists (VALIDATION_FAILED, `isOrderedList`), which have none. `GET public/categories` returns every active category by it (then oldest first), **whole, not paged**: an exception to `http.md`, "Lists" (*session*), since a keyset cursor follows `created_at` and the categories are a short list admins curate; the admin lists stay paged, newest first.
- **Products.** Status `draft`, `pending_review`, `published`, `rejected` plus an availability switch; fulfilment delivery, pickup or both; packaging trays, bags, vacuum or none (priced since issue #243, below); the cutting and packaging incompatibilities are global rules. *Session:* the approximate weight is whole grams; a size tag is optional and bilingual; limits 10 images, 20 sizes, 30 cuttings, 30 exclusions, 1,000,000 SAR per size, 10 t (`PRODUCT_LIMITS`).
- **Submission rules** (PRODUCT_NOT_SUBMITTABLE, 422, every reason at once): at least one size and one image, no offered cutting with an offered packaging it is incompatible with. A draft may be incomplete. *Session:* the rules apply on submission, on publishing a JAZLA product, to a change request and to an admin's edit of a published JAZLA product.
- **Editing.** A product under review takes no edit at all (PRODUCT_NOT_EDITABLE, 409, also availability and prices; *session*). On a published product, availability, fulfilment and prices apply at once, each price that changes with an audit entry (previous and new halalas); any other edit becomes the product's one pending change request (partial unique index) while the live version stays; approval applies it in one transaction; rejection keeps the request with the reason the vendor sees. **A change request never changes after it is created** (backend owner, review of #238; replaces "a second edit replaces the pending request"): a second edit, under the product's row lock, closes the pending request as `superseded` and opens a new one with a new id, so an admin approves exactly the content they saw; approving or rejecting a superseded request is PRODUCT_CHANGE_REQUEST_SUPERSEDED (409: reload), an unknown or decided one stays NOT_FOUND; the queue lists pending requests only and superseded ones are kept for history. The protection is in the server, not in a field the client must send. *Session:* a content edit, in any status, cannot change an existing size's, cutting's or (since issue #243) packaging's price (VALIDATION_FAILED, `isLivePrice`): prices change only at creation and through the prices edit. The repository enforces it too: a content save (an edit or an approved change request) never writes the price of a size or cutting the product keeps, so a price changed after a request was made survives its approval; and `min_price_halalas` is worked out from the stored `product_sizes` rows in the transaction that changed them, never from the request (review of #238: a size id named twice made it lower than every real price; one request now names each size and cutting style once, `isNotRepeated`). The request's content is JSONB, validated with zod when read. PRODUCT_NOT_EDITABLE also answers a review step on a product not waiting for one.
- **`min_price_halalas`** is written in the same transaction as any change to sizes (creation, content, prices, an approved request), from the stored sizes.
- **Writers lock the product row first** (backend owner, review of #238). Every use case that writes to a product or its children (sizes, cuttings, images, options, change requests) starts its transaction with `ProductRepository.lockForWrite` (`SELECT … FOR UPDATE`, through `lockProduct`), then reads the product and decides; creation has no row to lock. Why: working out the lowest price from the stored rows is not enough alone, since two price edits on different sizes each read the other's size before it commits; and an approval read before a price edit committed would write the old price back. With the lock, writers to one product run one after another. The in-memory fakes refuse a write without the lock, or one decided from a read of the product taken before the lock, so every use case test proves it. In e2e (`test/catalog.e2e-spec.ts`, "writers to one product at the same moment"): two price edits on different sizes at once store a wrong lowest price without the lock (proves the lock); a price edit sent while an approval runs waits for it (proves the lock orders them; the stored result there is right even without the lock); a price edit made after a change request keeps its prices through the approval (proves the kept-price rule alone). The general rule is in `modules.md` (writes to an aggregate lock its root row first).
- **Text search on the public product list** (2026-11-17, backend owner, issue #243): `q` on `GET public/products`, 2 to 100 characters after trimming, matching the name in Arabic or English, combined with every filter and the keyset paging; PostgreSQL only, no search service. Both sides are normalised by one SQL function, `catalog_search_text` (IMMUTABLE, in migration `20261117150000_catalog_design_followups`): Arabic diacritics U+064B to U+065F and U+0670 and tatweel removed, أ إ آ as ا, ى as ي, ة as ه, lowercased. `products.search_text` is kept by a `BEFORE INSERT OR UPDATE` trigger (code never writes it) and indexed with a GIN trigram index (`pg_trgm`, `products_search_text_idx`); the repository normalises the query through the same function (`SELECT catalog_search_text($1)`), escapes LIKE wildcards (`escapeLikePattern`) and filters with `contains`. *Session:* the in-memory fake carries a TypeScript copy of the normalisation for the use case tests only (`domain/fakes/search-text.fake.ts`); the e2e tests prove the SQL one.
  - **A query of only diacritics or tatweel** (`ًـ`) normalises to nothing and answers an empty page, never every product (`LIKE '%%'`); review of #244.
  - **The trigram index is not yet shown to serve the search** (backend owner, review of #244). On the seeded data (45 products, CI run 44112662177) PostgreSQL filtered `search_text` on the rows of the status index, even with sequential scans off: at that size it is the cheaper plan. Accepted for now. **To do once the staging server exists:** generate a large product set (tens of thousands, as the public list was measured on 50,000), run `EXPLAIN (ANALYZE, BUFFERS)` of the query the API sends for a 3-character-or-longer `q`, alone and with the category, vendor and meat type filters, and record the plans here; if `products_search_text_idx` is not used where it should be, decide the index (or a combined one) from those plans. Queries of 2 characters cannot use a trigram index at all.
- **Category images** (2026-11-17, backend owner, issue #243): a new public upload purpose `catalog.category-image` with the limits of `vendor.logo` (JPEG, PNG or WebP, 2 MB), uploadable by admins only; `categories.image_media_id` (nullable, `ON DELETE SET NULL`, indexed) set on an admin's create or update of the categories list (`imageMediaId`, null clears it), a ready file of that admin (MEDIA_NOT_FOUND, MEDIA_NOT_READY as for product images), refused on the other lists like `sortOrder` (VALIDATION_FAILED `isCategoryList`, even for null). Categories carry `imageUrl` (null without one) on `GET public/categories` and the admin list responses, read in bulk without a storage call (`MediaService.getPublicUrls`). *Session:* the image is checked whenever `imageMediaId` is sent, also when it is the current one (unlike product images, whose kept ones are not checked again); the seed gives each active category a placeholder uploaded by the admin development account, only when it creates the category.
- **Vendor pickers** (2026-11-17, backend owner, issue #243): vendors read what a product form offers on vendor routes (same guards and errors as the other vendor routes, tag `Vendor catalog lists`): `GET vendor/lists/:list` (`meat-types`, `cutting-styles`, `exclusion-items`; categories stay on `GET public/categories`) returns every active entry with both names, and `GET vendor/cutting-packaging-incompatibilities` every rule whose cutting style is active, with its name. **Whole, not paged**: an exception to `http.md`, "Lists", like the public categories, since they are short lists admins curate and a form needs all of them at once. *Session:* ordered oldest first (`created_at`, then `id`), stable whatever the language; the admin routes stay the only writers. The vendor catalog controller now has the prefix `vendor` (its product routes `products/...`, unchanged paths), one controller per audience as the admin one.
- **Packaging has a price** (2026-11-17, backend owner, issue #243): **this reverses the earlier "packaging has no price"**. Each packaging a product offers has an extra price (`product_packagings.extra_price_halalas`, 0 by default, never negative: `product_packagings_extra_price_check`) following the cutting price rules exactly: set at creation; a content edit cannot change a kept packaging's price (`isLivePrice`), a new one takes any price; changed only through the prices edit (`packagings: [{ packaging, extraPriceHalalas }]`; one the product does not offer is `isPackagingOfProduct`, a repeat `isNotRepeated`), at once even when published, under the product row lock, one audit entry per changed price (`packaging`, `previousHalalas`, `newHalalas`); an approved change request never writes a kept packaging's price. The shape of `packagings` in bodies and responses became `[{ packaging, extraPriceHalalas }]` (a breaking change, accepted: nothing is in production). Change requests stored before it hold bare names and are read as price 0, never rewritten (*session*).
- **JAZLA's products** (the platform vendor's): admins create, edit and publish them through admin routes, which act only on the platform vendor's products (another vendor's is NOT_FOUND); draft to published directly, with the submission rules. *Session:* an admin's edit of a published JAZLA product applies at once, audited (`catalog.product.updated`); NOT_FOUND (`PLATFORM_VENDOR_MISSING`) before `pnpm vendor:create-platform`.
- **Images** use the existing public purpose `catalog.product-image`, now open to the vendor and admin upload endpoints; a new image is a ready file of the signed-in user (another user's is MEDIA_NOT_FOUND); images already on the product are not checked again (*session*).
- **Public list performance** (*session*, measured on 50,000 products): one query (Prisma joins `vendors` and `categories` in it) on composite indexes `products_listing_idx` (status, is_available, created_at desc, id desc) and its category and meat type variants (`products_listing_category_idx`, `products_listing_meat_type_idx`), the vendor filter on `(vendor_id, status, created_at, id)`; the price range and the vendor and category conditions are checked on the rows read. Not partial indexes: Prisma sends the status as `CAST($1::text AS product_status)`, from which PostgreSQL cannot prove a partial index's condition, so the first migration's partial indexes were never used and `20261116000616_catalog_listing_indexes` replaced them. `keysetAfter` adds `createdAt <= cursor`, an index bound, so a deep page starts at the cursor (10,000 rows deep: 101 ms before, 0.3 ms after); this also serves the vendors lists. Cover images and vendor names come in two batched reads.
- *Session:* `cutting_packaging_incompatibilities_pair_key` breaks the `<table>_<columns>_key` naming: the full name passes PostgreSQL's 63-byte limit.
- *Session:* building blocks moved out of vendors unchanged, for the catalog: the bilingual DTOs, `ReasonDto`, `organisationOf`, `ADMIN_AUTH_ERRORS`, `OptionalLocalizedText`, the fakes' `keysetPage`, `InMemoryAuditLog`; `VENDOR_AUTH_ERRORS` added beside `ADMIN_AUTH_ERRORS`. The vendors e2e no longer deletes the platform vendor, which the catalog suite uses at the same time.

### Customers and account deletion (issue #239)

Decided 2026-11-17 by the backend owner (the approved plan and its decisions) unless marked *session*.

- **`customers` is a new CRUD-shaped module**, not part of `users`: `users` stays the identity of every user in every audience; what a customer keeps belongs to one audience, and orders will depend on it without touching identity. - **Profile** (FR-ACC-02): a full name of 2 to 60 characters (spaces tidied, invisible format characters removed; *session*), an optional email stored lowercase, neither verified nor unique, and the preferred language (`ar` or `en`, default `ar`). Complete once it has a full name; the email and the language do not count. The app may be used with an incomplete profile: the verify response (`profileComplete`, null for staff) and `GET /v1/customer/me` carry it. **Planned: the orders module requires a complete profile to place an order.**
- **`GET /v1/customer/me` returns the customer's own phone in full**, with the profile and the marketing consent; every other response, and every log, keeps phones masked. Staff `me` endpoints are unchanged.
- **Marketing consent** (NFR-PRV, PDPL): an insert-only history (`consent_records`, kind `marketing`), never updated or deleted, so consent can be proven later. The current state is the record with the highest per-customer sequence (1, 2, 3…, given under the row lock; unique index as the backstop), not the newest timestamp, so two servers' clocks cannot reorder it. Opt-in: no record means not granted; sending the current choice again records nothing (*session*).
- **Addresses** (FR-ACC-03): at most 10 (ADDRESS_LIMIT_REACHED, 409), each with a label (1 to 30), a map point (latitude and longitude, required, range-checked), optional readable fields filled by the app from reverse geocoding and editable (city, district, street, building, and the Saudi short national address: four letters then four digits, stored `ABCD1234`; *session*: 100 characters each, 300 for the driver's instructions). Exactly one default once any exist: the first address is the default, a new default clears the old one, deleting the default promotes the newest remaining one; the database guarantees at most one (partial unique index), the lock the rest. The list is unpaged, default first: an exception to `http.md`, "Lists", as for categories. **Built (issue #24):** each address says whether it is covered (`isCovered`, Coverage zones below); **orders copy the address at checkout**, so editing a saved address never changes an order (FR-ACC-03's lock on an address used by an active order comes with orders).
- **Account deletion** (`DELETE /v1/customer/me`, FR-ACC-05) is immediate, in one transaction in the auth module (which owns sessions and the sign-in time), calling the customers and vendors modules through ports: the user's row locked; refused for active vendor, kitchen or admin access (ACCOUNT_HAS_STAFF_ACCESS, 409, until it is removed), for a disabled user (ACCOUNT_DISABLED: such deletions go through support, because otherwise deleting and signing up again would get around a ban), and without a sign-in in the last 10 minutes (RECENT_SIGN_IN_REQUIRED, 403 rather than 401 so a client does not just refresh); then the pending and rejected vendor applications with their documents (an approved application is kept as its vendor's business record), the profile and addresses (the consent history is kept and ended withdrawn), every session in every audience with its refresh tokens, the phone's OTP challenges, and the user becomes a **tombstone**: `phone` null and `deleted_at` set (check constraint `users_deleted_check`). `users_phone_key` treats nulls as distinct, so the phone signs up again as a new user with nothing of the old one, while consent records, audit entries and reviews keep a valid id. An optional reason from a fixed list (`?reason=`; *session*: `not_using`, `privacy`, `bad_experience`, `other_account`, `other`, and a query parameter because an optional DELETE body is dropped by some clients) goes into the audit entry, never free text. Built without a phone hash on the tombstone (open question above). **Planned:** orders need a retention rule for invoices.
- **Personal data and what deletion does** (the table approved with the plan): `users` tombstoned; `customer_profiles`, `customer_addresses`, `auth_sessions`, `refresh_tokens`, `otp_challenges` deleted; `consent_records` kept (ids, choices, times); `vendor_applications` pending and rejected deleted, approved kept; `vendor.document` files marked OWNER_DELETED and removed by the media cleanup job after the commit; `audit_logs` kept unchanged (metadata holds ids and numbers only); `vendors` not reached (an active vendor is refused); logs hold ids and masked phones; backups keep everything for 30 days (NFR-AVL), which the privacy policy must say.
- **Races, and the locks that settle them** (*session*, reviewed with the plan): a sign-in holds the user's row with a shared lock while it creates the session (`UsersService.lockForShare`), so a deletion either deletes that session or commits first, and the sign-in then finds the phone free and signs in a new user; a vendor application holds the applicant's row the same way, so it never names a deleted account; the deletion deletes OTP challenges with `SKIP LOCKED`, because a challenge being consumed belongs to a sign-in that is waiting for the deletion (a deadlock otherwise) and that sign-in ends as the new user. A deletion racing an application's approval deadlocks at worst; PostgreSQL ends one and the transaction runner retries it: the approval then finds no application, or the deletion finds the new vendor access.
- **The 15-minute access token outlives a deletion** (as it outlives a logout): every customer endpoint that reads or writes the user answers UNAUTHORIZED, and so does submitting a vendor application; a file uploaded in that window is an unreferenced upload, left to the later cleanup of unreferenced files (Vendors, "Upload limits").
- **Files of a deleted account leave in two steps** (backend owner, review of #240): the media cleanup deletes a ready file's checked copy at its next run, and the row with its staging object only once the upload's confirm window has ended. Removing the row earlier broke "an upload is never removed while its upload URL is still valid": an upload to a still-valid ticket after the row was gone left an object no row names, which no cleanup finds. So a pending upload's staging object can outlive the deletion by up to `MEDIA_PENDING_UPLOAD_TTL_SECONDS` plus one cleanup interval.
- *Session:* a new upload rejection reason `OWNER_DELETED` (removed by the cleanup like `EXPIRED`, as above); `GeoPointDto` moved to `src/common/dto/` for reuse; `CUSTOMER_AUTH_ERRORS` beside the admin and vendor lists; the session's `created_at` is now written from the auth clock (`AuthSession.signedInAt`).

### Coverage zones (issue #24)

- **`coverage` is a new CRUD-shaped module** (no state machine, no money): `CoverageZonesService` (admins' list and changes, and the database side of the check) and `CoverageService` (the check, exported: `findZone(point)`, `isCovered(point)`). Every zone change is audited (`coverage.zone.created`, `updated`, `deleted`) in its transaction. Admins are the whole admin audience: there is no finer permission system yet. Each zone has a map colour for the dashboard editor (`color`, `#RRGGBB`, default `#6A1A20`, the brand's deep red; check constraint `coverage_zones_color_check`).
- **Polygons are PostGIS `geometry(Polygon, 4326)`** (`coverage_zones.polygon`, GIST index), GeoJSON in and out. The Prisma client cannot touch the column (`Unsupported`), so it is written and read through the geo helpers in `src/infra/database/` (`polygonFromGeoJSON`, `toGeoJSON`, `pointFromLatLng`; `isGeoJsonPolygon` and `isPointInPolygon` in memory), database rule 13. A polygon is refused with INVALID_POLYGON (422) when its rings are not GeoJSON rings or PostGIS finds it invalid (ST_IsValid: edges that cross, among others); the check constraint `coverage_zones_polygon_check` is the backstop. `GeoPoint` moved from customers to `src/infra/database/` for the helpers (the vendors domain keeps its own copy: `domain/` cannot import infra).
- **The check runs in memory on the cached active zones list** (Redis, `ActiveCoverageZonesCache`), loaded from the database on a miss; while the cache cannot answer, the database answers with ST_Covers on the GIST index. *Session:* the cache is versioned rather than deleted (a change increments a counter after its commit, and a list is written under the version read before loading it), because a plain delete loses to a reader that loaded the old list just before the commit and writes it after; lists expire after five minutes, the bound on staleness when Redis is down during a change. Overlapping zones: the oldest answers. A point exactly on an edge may answer either way in memory (ST_Covers counts it in).
- **Saved addresses carry `isCovered`**, worked out on every read (after the transaction of a write), so it follows zone changes. *Session:* the check's `zone` is `null` when not covered rather than absent, as every optional field of the API; the admin zones list is keyset-paged like every list.

  - **Required in production (foundation review, batch B).** With `NODE_ENV=production` the variable has no default and startup fails without it (an empty value counts as unset); elsewhere it defaults to 0. Forgotten behind a load balancer, 0 makes every customer share the load balancer's counter.
- **Rate limiting.** `@nestjs/throttler` 6.7.1, pinned exactly, with its guard global. The storage is our own `RedisThrottlerStorage` (`src/infra/rate-limit/`), built on the shared Redis client: one Lua script per request, fixed window, block on overflow, keys SHA-256-hashed under `<REDIS_KEY_PREFIX>:rate-limit:` (`jazla:rate-limit:` by default). Why not a package: the community storage the Nest documentation points to, `@nest-lab/throttler-storage-redis` 1.2.0 (last release 2026-02-03), declares peer `@nestjs/common` and `@nestjs/core` `^7 … ^11`, so it does not support Nest 12. Its predecessor `nestjs-throttler-storage-redis` 0.5.1 stopped in 2024 at Nest 10. Decided 2026-11-13 by the session, as the brief allowed.
- **The default limit is per client address across all endpoints.** The library's default key is per address per endpoint; ours (`clientRateLimitKey`) makes it one counter per address. `@RateLimit(...)` gives an endpoint a stricter limit on a counter of its own, so an OTP limit is not used up by browsing. Defaults: 300 requests per 60 s (`RATE_LIMIT_MAX_REQUESTS`, `RATE_LIMIT_WINDOW_MS`). The number is the session's: mobile carriers put many customers behind one address (carrier-grade NAT), so the default leaves headroom. Revisit with real traffic. Health is exempt (`@SkipRateLimit`). A request to an unknown route (404) is not counted by this limit, because guards run only on matched routes; the pre-routing limit counts it. Decided 2026-11-13 by the session.
- **Rate limiting fails open.** When the storage cannot count a request, the request is let through unlimited, with a warning logged once per outage and an info line when Redis answers again, except on fail-closed endpoints (next entry). "Cannot count" is: the shared client is not connected (Redis is then not called at all, so the request loses no time), Redis errors or answers unexpectedly, or a connected Redis does not answer within 500 ms. The same rule covers the pre-routing limit. The trade-off: while Redis is down nobody is rate limited, so a flood in that window reaches the API. Failing closed would turn a Redis outage into a full API outage, health excepted, for every customer, during exactly the failures (Eid peaks) when the platform is under most strain. Redis being down already shows in readiness and the logs. Decided 2026-11-13 by the backend owner (step seven brief); the timeout by the session.
  - **Correction (foundation review, batch B).** This entry claimed "the 500 ms bound keeps a slow Redis from slowing every request". It did the opposite while Redis was down: every request waited the full 500 ms, because the shared client held each command while reconnecting (the review measured 500 to 516 ms per request), and the e2e test hid it by giving the storage a client with test-only options. Now the storage checks the client's status first and skips Redis at once when it is not `ready`; the 500 ms applies only to a connected Redis that is slow. Tested with the production client class and options, Redis stopped mid-test: ten requests took 3 to 23 ms each.
- **Sensitive endpoints fail closed.** `@RateLimit({ ..., failClosed: true })` makes an endpoint answer 503 SERVICE_UNAVAILABLE while the rate limit storage is unavailable, instead of letting requests through unlimited. OTP endpoints use it, and so does any endpoint where an unlimited request costs money or is a security risk. Why: each OTP request sends an SMS, which costs money per message, so an unlimited window during a Redis outage is a direct bill and an SMS-pumping target; a 503 on OTP only delays logins while the rest of the API stays up. The default stays fail open. Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **Named rate limit counters.** Every `@RateLimit` names its counter (`otp-request`); the key is the name and the client address, not the class and method, which let two controllers with the same class name share one counter by accident (finding 7). Endpoints share a counter only by declaring the same name with the same settings; the same name with other settings, or a method `@RateLimit` under a class-level `@SkipRateLimit`, stops the application at startup (`RateLimitPolicyCheck`), naming the endpoints. Settings are validated when the file loads: positive whole numbers, and a block never shorter than the window. Decided 2026-11-13 by the backend owner (foundation review, batch B); the name format and the startup check through Nest's DiscoveryService by the session.
- **Blocking keeps the counter.** The rate limit script no longer deletes the counter when it blocks a client, so a client whose block ends inside the window is still over the limit and is blocked again by its next request (finding 6: OTP with a 1 minute block in a 10 minute window allowed about 50 requests instead of 5). Decided 2026-11-13 by the backend owner (foundation review, batch B).
- **Rate limit keys carry a cluster hash tag.** `jazla:rate-limit:{<sha256>}:hits` and `:blocked`: only the part in braces decides the Redis Cluster slot, so the script that touches both keys does not fail with CROSSSLOT on cluster-mode Redis (finding 9). Counters written under the old key format are ignored and expire with their window. Decided 2026-11-13 by the backend owner (foundation review, batch B).

The health checks are not counted. Decided 2026-11-13 by the backend owner (foundation review, batch B); the default and the shared window by the session.

Decided 2026-11-13 by the backend owner (step seven brief; JSON only in the foundation review, batch B); the 415 check by the session.

A request now has a body only with a Content-Length above 0 or a Transfer-Encoding (a chunked body counts even if empty: its length is unknown until read); a bodyless request passes whatever its type. Proven by `test/http-security.e2e-spec.ts` (fails with the old check). Decided 2026-11-14 by the backend owner.

### Integrations

- **Shape.** `src/integrations/<capability>/` holds a port (interface + injection token), types, errors, service, module, an `index.ts` public entry, and `providers/` with one file per vendor plus a fake. The folder and the word are "provider" (`resend.provider.ts`). Why *(inferred)*: one shape and one word, so any integration can be read by someone who has seen one.
- **List.** mail, sms, push, payments, storage, delivery, zatca, bnpl.
- **mail, sms, push.** An ordered provider list with fallback on retryable failures. An undocumented vendor error counts as retryable for these three. Why *(inferred)*: a message that is not sent costs more than a second attempt through another vendor.
- **payments.** Never fails over. One active provider takes new payments, each payment record stores its provider, and capture, void and refund go to that provider. An unknown or ambiguous gateway response marks the payment pending and triggers a status query. Why: a blind retry can charge the customer twice.
- **delivery and bnpl.** Like payments: the provider is recorded on the shipment or transaction, and every later call goes to that provider. No automatic failover.
- **zatca.** No fallback. Submissions go through a queue and retry against the same provider, with an idempotency key. Why: an invoice must never be submitted twice.
- **storage.** One provider, no fallback.
- **Test-only entry: `testing.ts` (R22).** Each integration has a second public entry, `testing.ts`, exporting its fake and test helpers; `index.ts` exports nothing test-only. Lint rule R22 refuses `testing.ts` from every source file except unit tests (`*.spec.ts`), the integration's own code included; `test/` is outside the boundary rules. Why: when the fake was exported from `index.ts`, production code could inject it with no rule to stop it. Decided 2026-11-14 by the backend owner (issue #229 corrections); the rule's mechanism (a policy dropped for spec files) by the session.
- **Storage, as built (issue #229).** The reference integration (ARCHITECTURE.md). Decided 2026-11-14 by the backend owner (task brief) unless marked *session*:
  - **Two buckets**, public and private, separated by bucket, never by path. Public objects get `STORAGE_PUBLIC_BASE_URL/<key>` (later a CDN); private ones only a presigned GET created on request.
  - **Presigned POST for uploads**, never PUT: the policy carries `content-length-range` and the exact Content-Type, which the storage enforces; a presigned PUT cannot limit size. The API never streams file contents.
  - **Keys are the server's**: `<purpose with dots as slashes>/<yyyy>/<mm>/<dd>/<media id>` (UTC date), prefixed `staging/` for the upload and extended `/<attempt id>` for the checked copy (below). The client's file name is sanitised display metadata (`sanitizeFileName`), never part of a key.
  - **Uploads are staged; only a checked copy is served** (review of #230, fixed in #234). A presigned POST is reusable until it expires, so an object at the ticket's key could be replaced after it was checked. The ticket is signed for a staging key in the private bucket, whatever the purpose's visibility, so nothing unchecked is ever publicly readable. Confirm copies the staging object (`copyObject`, inside the storage) to a final key in the purpose's bucket that no ticket names, checks that copy, marks the row ready with its location (`bucket`, `object_key`: null until ready, check constraint `media_ready_location_check`), then deletes the staging object; a rejection deletes both. Each confirmation attempt copies to its own key, so concurrent confirmations racing a re-upload cannot overwrite each other's checked copy: the conditional update's winner keeps its copy, a loser deletes its own. The client may still write the staging key until the ticket expires; it is never read, and the cleanup deletes it once the confirm window (always longer than the ticket) has ended (`staging_key` then null). Accepted: a process that dies between a copy and its update leaves an unreferenced copy; nothing serves it.
  - **Request, upload, confirm.** Confirm checks existence, size, and the real type from the first bytes of the checked copy (`detectContentType`); the declared Content-Type is not trusted. A failure deletes the object, then marks the row rejected with a reason. *Session:* a real type that is allowed but differs from the declared one is rejected too (CONTENT_TYPE_MISMATCH), because the storage serves the declared type with the file; a missing object at confirm is a rejection (OBJECT_MISSING), as the brief lists existence among the checks.
  - **SDK.** `@aws-sdk/client-s3`, `@aws-sdk/s3-presigned-post`, `@aws-sdk/s3-request-presigner` 3.1159.0, pinned exactly (*session*: the newest release at least two weeks old). Connection timeout 3 s and request timeout 10 s (`throwOnRequestTimeout`), because the SDK sets none; the SDK's own 3 attempts stay.
  - **Error mapping** (*session*). Every failure becomes `StorageError` with a `reason` and `retryable`: unavailable and throttled are retryable (SERVICE_UNAVAILABLE); access-denied, bucket-missing, object-archived and rejected are not (INTERNAL_ERROR); neither is the client's fault. A missing object is a result (null), not an error. The codes come from the `@throws` of each SDK command and the SDK's retry classification (`@smithy/core`), not from memory; HeadObject's 404 has no body, so a missing bucket reads as a missing object there.
  - **Upload purposes.** Two declared as examples, `catalog.product-image` (public, JPEG/PNG/WebP, 5 MB) and `vendor.document` (private, PDF/JPEG/PNG, 10 MB), in `UPLOAD_PURPOSES` in the media module (*session*: a lookup table that other modules extend, like QUEUE_NAMES, so purposes are typed and found in one place).
  - **Cleanup** (*session* for the mechanism). A BullMQ job scheduler (`keepJobScheduled`, every MEDIA_CLEANUP_INTERVAL_SECONDS) runs `MediaService.removeExpiredUploads`: one conditional update claims every expired pending row (rejected, EXPIRED), then each claimed row's object and then row are deleted. Idempotent and safe beside a concurrent run or a confirmation; a confirmation of a claimed row gets MEDIA_UPLOAD_EXPIRED. MEDIA_PENDING_UPLOAD_TTL_SECONDS must exceed the upload URL's expiry (schema).
  - **Local MinIO** (*session*). The official `minio/minio` image is no longer published; Chainguard's free MinIO build is used, pinned by digest. Bucket setup runs in the MinIO container's entrypoint, not a one-shot service, because `docker compose up --wait` fails when any container exits. MinIO does not implement per-bucket CORS (PutBucketCors: NotImplemented), so CORS is server-wide (`MINIO_API_CORS_ALLOW_ORIGIN`, localhost origins). **Per-bucket CORS is required of the production storage provider** (decided 2026-11-14 by the backend owner): browsers upload straight to the buckets with presigned POSTs, and each bucket must allow exactly the app origins it serves; a provider that, like MinIO, offers only server-wide CORS is not acceptable for production. Public buckets allow anonymous `s3:GetObject` only: mc's `download` preset also allows listing every key. The e2e tests use the `-test` buckets (`scripts/e2e.mjs`).
  - **No endpoints yet**: an unauthenticated upload endpoint would be abusable; the e2e tests use a controller in `test/support/`.

### Code rules

- **Type safety.** `any` and `@ts-ignore` are never allowed.
- **Errors.** `AppError` and the error code list live in `src/common/errors/`. Codes are UPPER_SNAKE_CASE. Business code throws `AppError` or a subclass, never a raw `Error` or a Nest `HttpException`. Codes are a contract with the mobile app: once released, never renamed or reused.
- **Money helper.** `src/common/money/`. Clients receive integer halalas. No shared package.
- **SMS, as built (issue #231).** The reference for ordered fallback (ARCHITECTURE.md); mail and push copy it. Decided 2026-11-14 by the backend owner (task brief) unless marked *session*:
  - **The port sends one text to one number** and returns the provider's message id and name; no bulk, scheduling or templates. The integration knows nothing about OTPs: codes, expiry and verification belong to the authentication module.
  - **Fallback.** SMS_PROVIDERS is the ordered list. A retryable failure (unreachable, timeout, 5xx, rate limit, or an error the vendor does not document) moves to the next provider; a non-retryable one (invalid number, rejected sender, invalid message, insufficient balance) stops. When no provider sent the message, one error (`SmsNotSentError`) carries every attempt with its cause. Each provider call has its own timeout.
  - **Startup** fails on an unknown provider or one missing its variables, and on the log provider in production. The log masks the number and never holds the text, and names the provider that sent each message.
  - **Providers**: `fake` (tests, through `testing.ts`), `log` (writes the whole message, so developers read OTP codes locally; the development default in `.env.example`), and Msegat only from its official documentation.
  - *Session:* **where startup checks run.** The environment schema refuses an unknown name, a name listed twice, a listed provider whose variables are missing (`SMS_PROVIDER_VARIABLES` with `findMissingProviderVariables`, so each new provider declares its variables in one table), and `log` in production: one clean line per variable, as for every other variable. Unset, SMS_PROVIDERS is `log` outside production and empty in production, and `SmsService` refuses an empty list when it starts. Why not required in production like TRUST_PROXY_HOPS: no provider is allowed in production yet, so a required variable would stop every production start; nothing imports `SmsModule` until authentication, and from then on production cannot start without a real provider.
  - *Session:* **one timeout, `SMS_PROVIDER_TIMEOUT_MS` (default 5000 ms), applied to each provider call separately**: each provider gets the whole time, so a list of n providers can take n times it. The call's `AbortSignal` aborts on timeout, so a provider passes it to its HTTP request. A per-provider value is one config field per provider when a vendor needs it.
  - *Session:* **the number is normalised before any provider is called**; a number that is not a Saudi mobile number, or an empty text, is an `SmsError` (invalid-number, invalid-message) with no provider called. `SmsNotSentError.retryable` is the last attempt's (false when the chain stopped on a non-retryable error). As for storage, clients see SERVICE_UNAVAILABLE when retryable and INTERNAL_ERROR when not: the module that sends (authentication) validates the number in its DTO, so an invalid number reaching the service is our fault.
  - *Session:* **logs**: one info line per sent message (provider, message id, masked number, encoding, units and segments from `measureSmsText`) and one warn line per failed attempt (provider, reason, retryable, the error). The text is never in either.
  - *Session:* **shared helpers.** `normalizeSaudiMobileNumber` accepts the national mobile range, 5 followed by 8 digits, without checking operator prefixes, so a newly assigned prefix is accepted; it accepts Arabic-Indic (٠ to ٩) and Extended Arabic-Indic (۰ to ۹) digits, mixed with Latin ones or not, converting them before the check (decided 2026-11-14 by the backend owner); it rejects other scripts' digits, parentheses and dots (only spaces and dashes are separators). `maskPhoneNumber` is the phone part of the reserved masking helper: `+966*******78` for a Saudi mobile number, otherwise every digit but the last two masked. `measureSmsText` follows 3GPP TS 23.038 (127 basic and 10 extension GSM-7 characters) with segment sizes 160/153 (GSM-7) and 70/67 (UCS-2), never splitting an extension character or a surrogate pair; Msegat's documentation charges by the same sizes.
  - **Msegat: pending official documentation of the send response** (*session*, 2026-11-14). Not built, because no official page documents what `sendsms.php` returns. What was tried:
    - `https://www.msegat.com/api/` links its guide at `https://documenter.getpostman.com/view/39158411/2sBXwqqqD2`: HTTP 404, the page and its collection alike.
    - `https://www.msegat.com/resource-center/` has no API documentation.
    - `https://www.msegat.com/faqs/` links `https://msegat.docs.apiary.io/`, which was reached: its API Blueprint (`https://msegat.docs.apiary.io/api-description-document`, last updated 2025-08-07) documents `POST https://www.msegat.com/gw/sendsms.php` with `userName`, `apiKey`, `numbers` (`966…`, no leading zeros), `userSender` (activated, at most 11 characters), `msg` and `msgEncoding` (`UTF8`), an optional `reqBulkId` ("when user need the msg id of the bulk"), and a list of result codes.
    - The gap: for `sendsms.php` it shows only "Response 200 (application/json)" and "Response 404 (text/plain)", with no body and no example. So it does not say which field carries the result code (other endpoints show `code` as the number `1`, the string `"1"` or `"M0000"`), which field carries the message id, or when the 404 is returned; and it gives no example to mock in tests. No rate limit response is documented either.
    - Needed to build it: a sample success response and a sample error response of `sendsms.php`, from Msegat support (`https://sanad.t2.sa`, Support@msegat.com) or an updated official page. Then it is one provider file, its test, one registration, `msegat` in `SMS_PROVIDERS` and its variables (user name, API key, sender name) in `SMS_PROVIDER_VARIABLES`.
    - The documented codes map, for then: invalid-number for 1120 and M0008; sender-rejected for 1110; invalid-message for 1050, 1064, 1140 and M0090; insufficient-balance for 1060. Decided 2026-11-14 by the backend owner:
      - **Credential and account codes** 1010 (variables missing), 1020 (invalid login info), M0001, M0002 and M0037 (send from a static IP) are **retryable**, so the next provider can send, and are **logged at error**, not warn, so an operator notices: the account is misconfigured and every message fails at Msegat until someone fixes it. *Session, for when the provider is built:* this needs a retryable reason of its own (for example `provider-misconfigured`) that the service logs at error; today every failed attempt is logged at warn.
      - **1061 (message duplicated) is not retryable**: the message probably arrived, and resending it through another provider would deliver two codes. *Session:* it maps to `invalid-message`, the closest non-retryable reason, unless the provider adds a reason of its own.
- **Append-only finance ledger.** Every movement of money (customer payment, commission, merchant payable, refund, COD receivable from the delivery company, transfer) is a ledger entry. Entries are never updated or deleted; a correction is a new entry. Why: statements and settlements must be reproducible from the entries alone.
- **Configuration.** `@nestjs/config` loads `.env` files; a zod schema (`src/config/env.schema.ts`) validates the environment once, in `src/config/load-env.ts`, the only file that reads `process.env` (R11). The typed namespaces (`registerAs`: `app`, `logger`, `database`, `redis`, `queue`, `http`, `rateLimit`, `storage`, `media`, `sms`) share that one result. `main.ts` waits for `ConfigModule.envVariablesLoaded` and calls `loadEnv()` before creating the app, so an invalid environment prints only one line per offending variable (what was expected, never the value) and exits with code 1, with no Nest log before it. `NODE_ENV` defaults to `development`. Decided 2026-11-13; the single validation and the clean exit replaced the first version the same day.
- **Error responses.** `{ code, message, details?, requestId }`, status in the status line, written only by the global `AllExceptionsFilter`. Messages come from one catalogue in Arabic and English; English only when `Accept-Language` ranks it above Arabic. No i18n library. Decided 2026-11-13.
- **Mapping Nest exceptions.** An HttpException gets the code for its status: 400 BAD_REQUEST, 401 UNAUTHORIZED, 403 FORBIDDEN, 404 NOT_FOUND, 405 METHOD_NOT_ALLOWED, 409 CONFLICT, 413 PAYLOAD_TOO_LARGE, 415 UNSUPPORTED_MEDIA_TYPE, 429 RATE_LIMITED. Another 4xx keeps its status with BAD_REQUEST, another 5xx keeps its status with INTERNAL_ERROR. VALIDATION_FAILED is produced only by the validation pipe, because clients read it as "the input was wrong". Malformed JSON is BAD_REQUEST. The exception's own message is never sent. Decided 2026-11-13 by the backend owner, replacing the session's first mapping.
- **Pretty logs only when available.** pino-pretty (a dev dependency) is used only when `NODE_ENV` is development and the package resolves; otherwise logs are JSON. Decided 2026-11-13.
- **Validation details.** `details` of VALIDATION_FAILED is `[{ field, constraints }]`: dotted field paths and class-validator constraint names (`isInt`, `whitelistValidation`), not messages, so they are stable and language-neutral. Decided 2026-11-13 by the session.
- **Request ids.** The incoming `x-request-id` is reused when it is at most 128 characters of `A-Z a-z 0-9 . _ : -`, otherwise replaced by a UUID. Decided 2026-11-13 by the session. Why: reusing a client's id ties its logs to ours; the limits stop log injection and oversized values.
- **Logging.** pino through nestjs-pino. One line per completed request: info, warn for 4xx, error for 5xx with the original error (the filter hands it to the logger as `response.err`). Readable through pino-pretty in development, JSON in production, silent in test. What a line may hold is decided by allowlists, in one place (`createLoggerParams`): errors keep name, message, code, stack and cause only (ioredis put the Redis password in `err.command`, Prisma whole rows in `err.meta`); requests are logged with the path only (no query string), `req.ip` and allowlisted headers; secret-like fields are redacted at any depth, case-insensitively, by walking each line in `formatters.log`, because pino's path-based `redact` matches exact, case-sensitive paths only. A Prisma error (any `PrismaClient*` class) is logged with its class name, code, model (`meta.modelName`) and stack frames, and a fixed message in place of its own: a validation error prints the query with its argument values, a phone number among them. Decided 2026-11-13; the allowlists replaced path redaction the same day (foundation review, batch A); the Prisma message in batch B.
- **e2e coverage.** An e2e test covers every case that applies to its endpoint among success, invalid input, authentication and ownership. Decided 2026-11-13.
